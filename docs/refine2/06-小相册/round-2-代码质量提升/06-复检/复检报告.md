## 三、BUG 详情与修复

### BUG-1: 批量删除成功后未同步 committedCoverMediaId

| 项 | 值 |
|----|----|
| 严重度 | MEDIUM |
| 类型 | 瞬态状态不一致 |
| 文件 | `RealPostEditingViewModels.kt` |
| 位置 | L322-325（save() 批量成功分支）|
| FR | FR-5 |

**问题描述**：
批量移除媒体成功后，`committedMediaIds` 正确更新，但 `committedCoverMediaId` 未同步。如果被删媒体包含当前封面，服务端会自动将封面回退到剩余首个媒体，但本地 `committedCoverMediaId` 仍为已删除的旧封面 id。

**影响场景**：
1. 用户删除封面媒体 A，UI 自动切到 B
2. 批量移除成功 → 服务端封面回退为 B
3. 本地 `committedCoverMediaId` 仍为 A
4. 后续封面更新（L345）: `finalCoverId(B) != initialCoverMediaId(A)` → 触发封面 API
5. 若封面 API 成功 → 状态一致（但多了一次不必要的 API 调用）
6. **若封面 API 失败** → `committedCoverMediaId` = A，经 L359 `takeIf` 过滤后 = null，本地认为无封面，与服务端 B 不一致

**修复**：
```kotlin
is ApiResult.Success -> {
    mediaChanged = true
    committedMediaIds = committedMediaIds.filterNot { removedIds.contains(it) }
    committedCoverMediaId = batchResult.data.coverMediaId  // 新增：从服务端响应同步封面
}
```

**修复验证**：Android 编译通过。

### BUG-3: PostMediaMergeUtils 重复 id 边界

| 项 | 值 |
|----|----|
| 严重度 | LOW |
| 类型 | 理论边界问题 |
| 文件 | `PostMediaMergeUtils.kt` |
| 位置 | L33-38（第二轮循环）|
| FR | FR-7 |

**问题描述**：
第二轮循环遍历原始 `latestItems`（未去重），而第一轮使用的 `latestById` 是去重后的 map。若 `latestItems` 存在重复 id，第二轮的判断 `id !in currentIds && id !in previousBaselineIds` 不会感知到本轮已添加过该 id，导致重复追加。

实践中远端接口返回唯一 id 列表，此问题不会触发，但与第一轮的去重逻辑不一致。

**修复**：将第二轮循环从 `latestItems.forEach` 改为 `latestById.forEach { (id, media) -> }`，天然去重且与第一轮一致。

```kotlin
// 修复前
latestItems.forEach { media ->
    val id = latestIdSelector(media)
    if (id !in currentIds && id !in previousBaselineIds) {
        add(transformLatest(media))
    }
}

// 修复后
latestById.forEach { (id, media) ->
    if (id !in currentIds && id !in previousBaselineIds) {
        add(transformLatest(media))
    }
}
```

**修复验证**：Android 编译通过。
