# 08-系统媒体 需求文档

> 版本: v1.0 | 日期: 2026-07-12 | 状态: 已确认
> 基于: 调研报告 2026-07-12 + 用户反馈

## 一、模块目标

将系统媒体模块从"功能完整但代码臃肿、刷新体验差、导入状态不稳、16列卡顿"的状态，提升为"架构清晰、刷新流畅、导入准确、视觉精致"的本机媒体工具区。核心改进：拆分 3 个巨型文件（9400 行→12+ 文件），重构刷新机制为后台静默模式，修复导入状态和时间滑条 Bug，新增系统相册筛选，升级网格和 Viewer 视觉品质，优化 16 列性能。服务端本轮无变更。

### FR-8: 刷新机制重构

**描述**: 当前进入页面自动刷新导致按钮长时间旋转、阻塞手动操作、新增/删除不能及时更新。重构为后台静默刷新 + 手动按需刷新。

**端**: Android

**优先级**: P0

**验收标准**:
- AC-1: 进入页面时若缓存有效（< 5 分钟），直接显示缓存数据，后台静默刷新
- AC-2: 后台刷新不触发手动刷新按钮的 loading 动画
- AC-3: 手动点击刷新按钮后才显示 loading 旋转
- AC-4: 新增/删除媒体通过 ContentObserver 或 MediaStore 变更监听及时感知（< 3 秒）
- AC-5: 后台刷新期间网格可正常交互（滚动/点击/多选）
- AC-6: 强制刷新（下拉或按钮）等待完成后更新 UI

**涉及文件**:
- `feature/photos/SystemMediaViewModel.kt` — 刷新逻辑重构
- `feature/photos/SystemMediaRepository.kt` — 缓存时效判断 + ContentObserver 注册
- `feature/photos/SystemMediaScreen.kt`（或拆分后）— 刷新按钮状态绑定

## 三、非功能需求

### NFR-1: 编译性能
拆分后 Android 增量编译时间不应显著增加（目标：增量编译 < 90 秒）。

### NFR-2: 运行时性能
16 列模式滚动帧率 ≥ 55fps。刷新操作不阻塞 UI 线程。

### NFR-3: 向后兼容
所有变更不得破坏现有入口（照片模块→系统媒体、生活控制台→系统媒体上传）。

## 四、范围边界

### 在范围内
- 三个大文件拆分重构
- 重复代码清理
- 刷新机制重构
- 导入状态准确性修复
- 时间滑条回弹 Bug 修复
- 系统相册筛选新增
- 去掉筛选文案
- 网格和 Viewer 视觉升级
- 缩放动画美化
- 16 列性能优化
- 测试骨架搭建

### 不在范围内
- 不改系统回收站协议
- 不重做上传分片/转码/CDN
- 不把系统媒体做成 App 内容评论/原图体系
- 服务端本轮无变更（除非 FR-10 排查发现服务端问题）

## 五、跨模块依赖

| 依赖模块 | 依赖方向 | 依赖内容 | 影响说明 |
|---------|---------|---------|---------|
| 照片流 | 系统媒体 → 照片流 | 导入后通知照片流刷新 | FR-8 刷新重构需保持 RealBackendMutationBus 通知不变 |
| 小相册 | 系统媒体 → 小相册 | 创建/加入小相册 | FR-1 拆分不改变上传接口 |
| 上传/传输中心 | 系统媒体 → 上传 | 三段式上传 | FR-1 拆分 UploadManager 需保持上传流程不变 |
| Viewer(07模块) | 系统媒体 → Viewer | 共享 ViewerZoomState | FR-4 替换为共享 ZoomState |
| PhotoFeedTimeScrubber | 系统媒体 ← 照片流 | 共享时间滑条组件 | FR-11 修复可能涉及共享组件 |
| YingShiApp | 路由 | 系统媒体/Viever 路由 | FR-2/FR-3 拆分不改变路由接口 |

## 七、风险清单

| # | 风险 | 严重度 | 缓解措施 |
|---|------|--------|---------|
| 1 | FR-1 BridgeRepository 拆分引入回归（上传/overlay/持久化） | 高 | 拆分后逐功能回归，保持外部接口签名不变 |
| 2 | FR-8 刷新重构导致数据不一致 | 高 | ContentObserver 监听 + 缓存时效双重保障 |
| 3 | FR-10 导入状态根因可能在服务端 | 中 | 先客户端排查，若发现服务端问题再扩展范围 |
