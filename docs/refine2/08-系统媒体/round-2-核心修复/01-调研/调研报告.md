## 二、FR-8 刷新机制重构 — 调研结果

### 2.1 现有刷新流程

**SystemMediaViewModel.kt（共 179 行）**:
- `init` (line 35-50): 进入页面立即 `refresh(forceRefresh = true)`，无缓存时效判断（缓存为空才走 `refresh()`，否则直接显示缓存并强制重刷）
- `refresh(forceRefresh: Boolean)` (line 59-111): 单一 `isRefreshing` 状态字段，无法区分后台刷新和手动刷新
- `publishState` (line 146-161): 调用 `LocalSystemMediaBridgeRepository.applyOverlay(rawItems)` 合并导入状态
- `handleBridgeMutation(event)` (line 132-144): 监听 bridge mutation，根据 kind 触发 `refresh(forceRefresh = true)` 或 `refreshLocalState()`
- `refreshJob` 单一 Job：新刷新请求到来时若旧任务还在跑则只记录 `pendingForceRefresh`，不会取消旧任务

**SystemMediaRepository.kt** (`LocalSystemMediaRepository` 类):
- `peekCachedMedia()` (line 54-57): 调用 `LocalSystemMediaQueryCache.peek()` + 预热 overlay
- `loadMedia(forceRefresh)` (line 59-74): 若 `!forceRefresh` 则返回 `peek()` 结果；否则 `dataSource.queryMedia()` 重新查 MediaStore
- `withAppImportStatus(allowRemoteRefresh)` (line 76-131): 服务端 import-status 合并，双指纹策略

**LocalSystemMediaQueryCache** (line 140-274):
- `peek()` (line 147-152): 先看 `memoryItems`，再看磁盘
- `store()` (line 154-158): 同时更新内存和磁盘
- `invalidate(context)` (line 160-165): 清内存 + 清磁盘 ItemsKey
- **无时间戳字段** — 缓存无时效概念

**SystemMediaComponents.kt - SystemMediaTopBar** (line 179-200):
- `isRefreshing` 为 true 时替换刷新按钮为 CircularProgressIndicator
- 这导致后台刷新时按钮也被替换为旋转动画

### 2.2 根因定位（R8-1 ~ R8-6）

| 根因 | 文件 / 行号 | 描述 |
|------|------------|------|
| **R8-1** | SystemMediaViewModel.kt:73 | `isRefreshing` 单一字段，无法区分后台刷新和手动刷新 |
| **R8-2** | SystemMediaRepository.kt:140-274 | `LocalSystemMediaQueryCache` 无时间戳字段，`peek()` 无时效判断 |
| **R8-3** | 全局缺失 | 无 ContentObserver 监听 MediaStore 变更（新增/删除媒体感知不及时） |
| **R8-4** | SystemMediaComponents.kt:179-200 | 刷新按钮被 loading 替换，无论后台还是手动 |
| **R8-5** | SystemMediaScreen.kt | 无下拉刷新控件（用户无显式触发后台→前台刷新的手势） |
| **R8-6** | SystemMediaViewModel.kt:35-50 | `init` 中 `refresh(forceRefresh = true)` 无条件强制刷新（已有缓存也强制） |

### 2.3 修复方向

1. **拆分 isRefreshing 状态**: 新增 `isBackgroundRefreshing` 字段（后台静默刷新用），保留 `isRefreshing`（仅手动按钮触发时为 true）
2. **缓存时效判断**: `LocalSystemMediaQueryCache` 新增 `storedAtMillis` 字段，`peek()` 增加 `maxAgeMillis` 参数（5 分钟）。过期返回 null
3. **ContentObserver**: 新建 `SystemMediaContentObserver` 注册到 `MediaStore.Files.getContentUri("external")`，onChange 触发后台刷新
4. **刷新按钮 UI**: `isRefreshing`（手动）才显示 loading；`isBackgroundRefreshing` 隐藏，按钮保持可点
5. **下拉刷新**: SystemMediaScreen 外层添加 `PullToRefreshBox`，触发 `refresh(forceRefresh = true)`
6. **init 优化**: 检查缓存时效，未过期直接用缓存不触发强制刷新；过期才触发后台刷新

## 三、FR-10 导入状态准确性修复 — 调研结果

### 3.1 双指纹策略现状

**SystemMediaImportPreview.kt** (共 251 行):
- `stableImportSourceKey()` (line 154-166): 基于 mediaStoreId 的指纹
  - 对 `store:` 类型: `store:image:12345`（稳定）
  - 对 `picked-` 类型: 回退到 metadata 指纹
  - 对 uri 类型: `uri:content://...`
- `stableImportMetadataKey()` (line 186-205): 包含 `displayTimeMillis`（line 197）
  - 格式: `meta:image|mimetype|displayname|sizebytes|displaytimemillis|wxh|duration`
- `stableImportSourceFingerprint()` (line 168-173): SHA-256(stableImportSourceKey)
- `stableImportMetadataSourceFingerprint()` (line 175-180): SHA-256(stableImportMetadataKey)
- `normalizeSystemMediaForImport()` (line 125-152): 上传时归一化 displayTimeMillis（按 MediaTimePreference 重新计算）

**SystemMediaRepository.kt - withAppImportStatus()** (line 76-131):
- 客户端查询时发送两个指纹（line 87-88: `stableImportSourceFingerprint()` + `stableImportMetadataSourceFingerprint()`）
- 服务端返回时按 `status.sourceFingerprint` 字段匹配（line 98）
- 客户端匹配时也尝试两个指纹（line 110-111）

**SystemMediaUploadReal.kt:286** + **SystemMediaUploadSupport.kt:756**:
- 上传时 `sourceFingerprint = mediaItem.stableImportMetadataSourceFingerprint()`（**只发 metadata 指纹**）

**服务端 MediaService.java:230-276 - getImportStatus()**:
- 只按 `sourceFingerprint` 字段查询: `findByLibraryIdAndSourceFingerprintInAndDeletedAtIsNull` (line 241)
- 服务端 MediaEntity 只有 `sourceFingerprint` 一个字段（line 90），没有 `sourceMetadataFingerprint` 字段
- 客户端发两个指纹上来，服务端只查 `sourceFingerprint` 字段，所以两个指纹都会被尝试匹配

| 根因 | 文件 / 行号 | 描述 |

### 3.3 修复方向

**核心修复（客户端）**:
1. **统一指纹策略（R10-1/R10-2/R10-3）**:
   - 方案 A（推荐）: metadata 指纹不再包含 `displayTimeMillis`，避免归一化前后不一致
   - 方案 B: 上传时也用源指纹 + metadata 指纹（同时存两个字段，服务端扩展 `sourceMetadataFingerprint` 列）

2. **持久化 invalidatedAppMediaIds（R10-4）**: `ImportOverlayStore.persistImportOverlay()` 增加 `invalidatedAppMediaIds` 序列化；`warmPersistentImportOverlay()` 读取

## 四、FR-11 时间滑条回弹 Bug — 调研结果

### 4.1 Bug 现象

拖拽时间滑条过程中，网格自动跳回顶部（或某固定位置）。在所有密度下复现。

### 4.2 直接根因

**SystemMediaScreen.kt:797-836 - onSeekToProgress**:
- line 820: `renderedCount = nextRenderedCount`
- 当用户拖拽到 visibleItems 之外的目标位置时，`onSeekToProgress` 会扩展 `renderedCount`
- `renderedCount` 变化 → `visibleItems` (derivedStateOf, line 217-225) 重新计算
- `visibleItems` 变化 → `gridBlocks` (remember(visibleItems, density), line 226-228) 重新构建
- `gridBlocks` 变化 → `scrubberTargetBlockIndexByMediaId` (line 229-231) 重新构建
- → `LazyVerticalGrid` 触发 relayout
- relayout 后 `gridState.firstVisibleItemIndex` 变化 → 触发 onSeekToProgress 计算 progress → 形成循环

**对比 PhotoFeedScreen.kt（照片流无此 Bug）**:
- `PhotoFeedTimeScrubber` 共享组件在照片流中使用 `scrollAnchors` 预计算
- onSeekToProgress 不修改 item 列表，只调 `scrollToItem`

### 4.3 连锁反应路径

```
用户拖拽滑条
  ↓
onSeekToProgress(progress)
  ↓
targetIndex 超出 visibleItems.size
  ↓
renderedCount = nextRenderedCount  ← line 820
  ↓
visibleItems (derivedStateOf) 重新计算
  ↓
gridBlocks 重新构建
  ↓
LazyVerticalGrid relayout
  ↓
gridState.firstVisibleItemIndex 变化
  ↓
displayedScrubberProgress 重算
  ↓
滑条 UI 跳到错误位置 → "回弹"
```

### 4.4 修复方向

**推荐方案 A**（拖拽期间冻结布局）:
1. `scrubberInteracting` 变为 true 时（onInteractingChanged, line 837-846），一次性扩展 `renderedCount` 到全量（`uiState.filteredItems.size`）
2. 拖拽过程中 `onSeekToProgress` 不再修改 `renderedCount`，只调 `scrollToItem`
3. 拖拽结束（`scrubberInteracting = false`）后恢复渐进式 `renderedCount`（可选，节省内存）

**优势**:
- 修复回弹
- 拖拽期间滚动流畅（已全部渲染）
- 内存开销可接受（拖拽期间临时全量，松手后回收）

**备选方案 B**（使用预计算 anchors）:
- 仿照照片流预计算 scrollAnchors
- 复杂度高，需要重写 scrubber helper

**选方案 A**。

## 五、FR-14 16列模式卡顿优化 — 调研结果

### 5.1 现有 16 列渲染逻辑

**SystemMediaGrid.kt**:
- `systemMediaThumbnailWarmWindow(OVERVIEW_16) = 420` (line 375): **预热窗口过大**
- `systemMediaThumbnailWarmBatchSize(OVERVIEW_16) = 18` (line 385): 18 个并发解码
- `systemMediaThumbnailRequestSize(OVERVIEW_16) = 96` (line 365): 96px 边长
- `buildSystemMediaGridBlocks()` (line 389-444): 16 列仅年份头（line 406-413），但全量构建
- 16 列已禁用多项视觉：animateItem、YingShiMediaFrame、视频时长 badge、已导入 badge、选中缩放、淡入动画、选中闪光

**SystemMediaThumbnail.kt**:
- `SystemMediaOverviewThumbnailCacheMaxBytes = 24MB` (line 27): 96px 缩略图约 36KB/张，**最大缓存约 682 张**
- `SystemMediaImageThumbnailCacheMaxBytes = 64MB` (line 28): 常规层
- `rememberSystemMediaThumbnail()` (line 30-59): 使用 `produceState` 触发重组
- `prefetchSystemMediaThumbnail()` (line 74-94): 预取，`Dispatchers.IO`
- `SystemMediaVideoThumbnailCache` (line 244-246): `ConcurrentHashMap<String, Bitmap>` **无界**，内存泄漏风险
- `SystemMediaBitmapThumbnailCache` (line 248-326): 双层 LRU（24MB+64MB）

### 5.2 性能瓶颈排序

| 优先级 | 瓶颈 | 文件/行号 | 描述 |
|--------|------|----------|------|
| **P0** | 缓存容量 < 预热窗口 | SystemMediaThumbnail.kt:27 + SystemMediaGrid.kt:375 | 24MB 缓存最多约 682 张 96px 缩略图，预热窗口 420 项 → 快速滚动时 thrashing（边加边淘汰） |
| **P0** | 预热窗口远超可见区域 | SystemMediaGrid.kt:375 | 420 项预热 vs 实际可见 ~240 项 → 浪费解码资源 |
| **P1** | 共享 Dispatchers.IO | SystemMediaThumbnail.kt:51, 85 | 18 并发解码 + 其他 IO 操作 → 线程饱和 |
| **P1** | 全量 gridBlocks 构建 | SystemMediaGrid.kt:389-444 | 16 列虽然只渲染年份头，但 SimpleDateFormat 全量格式化（每项都调） |
| **P1** | produceState 触发重组 | SystemMediaThumbnail.kt:39-58 | 每张缩略图加载完成后触发 Compose 重组 |
| **P2** | 滚动进度计算每帧迭代 | SystemMediaScrubber.kt:215-236 | `calculateSystemMediaScrollProgress()` 每帧迭代 visibleItemsInfo |
| **P2** | 视频缩略图缓存无界 | SystemMediaThumbnail.kt:244-246 | `SystemMediaVideoThumbnailCache` 是无界 ConcurrentHashMap，长会话内存泄漏 |

### 5.3 修复方向

1. **增大 16 列缓存容量** (P0): `SystemMediaOverviewThumbnailCacheMaxBytes` 从 24MB → 48MB（~1365 张），覆盖预热窗口
2. **减小预热窗口** (P0): `systemMediaThumbnailWarmWindow(OVERVIEW_16)` 从 420 → 240（与可见区域匹配）
3. **预热批大小减半** (P1): `systemMediaThumbnailWarmBatchSize(OVERVIEW_16)` 从 18 → 10，避免 IO 饱和
4. **gridBlocks 复用** (P1): 16 列构建时缓存 SimpleDateFormat 实例（已 outside loop），无需每项 new
5. **视频缩略图缓存加 LRU** (P2): 用 `LruCache<String, Bitmap>` 替代 `ConcurrentHashMap`，maxSize 32MB
6. **滚动进度计算优化** (P2): `calculateSystemMediaScrollProgress` 使用二分查找替代线性迭代

## 七、技术约束

### 7.1 服务端约束
- 本轮**不改服务端**：FR-10 选用方案 A（metadata 指纹去掉 displayTimeMillis），不扩展 MediaEntity schema
- 服务端 `MediaService.getImportStatus()` 行为不变（仍按 `sourceFingerprint` 单字段查）
- 因上传时存的是 metadata 指纹，去掉 displayTimeMillis 后客户端查询时算出的指纹与上传时一致，匹配成功

### 7.2 Android 端约束
- **Compose BOM 2024.09.00**: 对应 Compose UI 1.7.x
- **下拉刷新**: 使用 `androidx.compose.material3.pulltorefresh.PullToRefreshBox`（material3 1.3+）
- **ContentObserver**: 在 ViewModel 中注册，`onCleared()` 时注销；使用 `AndroidViewModel.applicationContext` 取 `ContentResolver`
- **SharedPreferences**: 沿用现有方案，不引入 DataStore

### 7.3 编译约束
- Android: `gradlew.bat assembleDebug` 必须通过
- Server: `mvnw.cmd compile` 必须通过（本轮不改服务端代码，仅验证编译）
- 单文件不超过 1200 行

### 7.4 兼容性约束
- 删除缓存中的 `importedAppMediaId` 字段需要考虑向后兼容：旧版本 App 写入的缓存新版本读取时，`optNullableString` 返回 null，不影响功能
- `invalidatedAppMediaIds` 持久化 schema 新增字段，旧 overlay JSON 无此字段时为空集合，向后兼容
