## 三、发现的 Bug

### BUG-1: `pickedItemUsesMetadataKeyPath` 测试假阳性风险（P1）

**问题**:
复检 Agent-1 在代码质量审查中发现，`SystemMediaImportPreviewTest.kt` 中 `pickedItemUsesMetadataKeyPath` 测试用例（L271-299）存在假阳性风险——即使被测的 picked-metadataKey 分支被破坏、回退到 URI 路径，测试仍会通过。

**根因**:
原测试构造了两个 picked item：
```kotlin
val first = sampleSystemMediaItem(id = "picked-abc-123", mediaStoreId = 0L, ...)
val duplicate = sampleSystemMediaItem(id = "picked-xyz-456", mediaStoreId = 0L, ...)
```
两者 `mediaStoreId` 均为 `0L`。而 `sampleSystemMediaItem` 内部用 `mediaStoreId` 生成 URI：
```kotlin
uri = UriTestDouble("content://media/external/images/media/$mediaStoreId")
```
因此两个 item 的 URI 完全相同（`content://media/external/images/media/0`）。

`buildSystemMediaImportPreview` 的 sourceKey 优先级为 `mediaStoreId > picked 路径 > uri > metadata`。当 picked 分支正常工作时，两个 item 因 displayName/sizeBytes 相同走 metadataKey 路径被分到同一组（duplicate 标记为 DUPLICATE_IN_SELECTION）。但如果 picked 分支被破坏、回退到 URI 路径（`"uri:$uriString"`），两个 item 仍因 URI 相同被分到同一组——测试仍通过，无法捕获回归。

**修复**:
将 duplicate item 的 `mediaStoreId` 从 `0L` 改为 `1L`，使两者的 URI 不同（`...media/0` vs `...media/1`）：
```kotlin
val duplicate = sampleSystemMediaItem(
    id = "picked-xyz-456",
    mediaStoreId = 1L,  // 原 0L → 1L，使 URI 不同，隔离 metadataKey 路径与 URI 路径
    displayName = "vacation.jpg",
    sizeBytes = 1_000_000L,
)
```
修复后，只有走 metadataKey 路径（displayName/sizeBytes/mimeType 相同）才会被分到同一组；若回退到 URI 路径则不会分组，测试会失败，从而能捕获 picked 分支回归。

**验证**:
重跑测试：
```bash
gradlew.bat testDebugUnitTest --tests "com.example.yingshi.feature.photos.SystemMediaImportPreviewTest"
```
结果: BUILD SUCCESSFUL，Exit Code 0，12/12 PASS。

**状态**: ✓ 已修复并验证
