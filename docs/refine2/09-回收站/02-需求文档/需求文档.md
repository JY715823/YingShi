# 09-回收站 需求文档

> 版本: v1.0 | 日期: 2026-07-19 | 状态: 已确认
> 基于: 调研报告 2026-07-19 + 用户反馈
> 上轮状态: implementing (2026-06-25, 未 closed)

## 一、模块目标

将回收站模块从"功能完整但代码臃肿(4182行)、导航异常、待清理入口消失、详情排版粗糙"的状态，提升为"架构清晰、导航正确、两阶段删除完整、视觉精致、数据清理彻底"的数据安全模块。核心改进：拆分巨型文件、修复 Viewer 退出导航、恢复待清理入口、优化详情排版、确保 purge 真正从对象存储和数据库删干净不留僵尸数据。服务端本轮无变更（除非 FR-10 排查发现后端问题）。

## 二、功能需求

### FR-1: RealTrashScreens.kt 拆分重构

**描述**: 将 4182 行的 RealTrashScreens.kt 拆分为 4-5 个职责清晰的文件。

**端**: Android

**优先级**: P0

**验收标准**:
- AC-1: 拆分后无单一文件超过 1200 行
- AC-2: 所有现有功能回归通过（四类列表/详情/待清理/Viewer/恢复/移出/永久删除）
- AC-3: 编译通过，无新增 warning
- AC-4: 外部调用方（YingShiApp.kt）通过原接口访问，路由签名不变
- AC-5: 各子模块职责清晰：列表、详情、待清理、Viewer

**涉及文件**:
- `feature/photos/RealTrashScreens.kt` — 缩减或拆分为入口文件
- `feature/photos/RealTrashListScreen.kt` — 新建，四类列表+分类切换+缓存

### FR-6: Viewer 退出导航修复

**描述**: 从回收站查看态系统返回后，应回到回收站列表，而不是跳到照片页/相册页。小相册查看态同理。

**优先级**: P0

**验收标准**:

- AC-2: 从回收站小相册 Viewer 按系统返回 → 回到回收站列表
- AC-3: 从回收站大相册 Viewer 按系统返回 → 回到回收站列表
- AC-4: 从通知进入回收站详情 → Viewer → 返回 → 仍在回收站
- AC-5: `photosTopDestinationName` 在 Viewer 退出后保持 TRASH 不变

**涉及文件**:

- `feature/photos/RealTrashViewer.kt`（FR-1 拆分后）— Viewer 退出回调

### FR-9: 24h 待清理入口恢复 + purge 彻底清理

**描述**: 待清理入口消失需恢复。确保从待清理页执行 purge 时，真正从对象存储(MinIO)和数据库中删干净，不留僵尸数据（评论/关系/trash记录/物理文件）。

**端**: Both

**优先级**: P0

**验收标准**:
- AC-1: 分类菜单中有待清理条目时显示"待清理"入口
- AC-2: 点击入口进入待清理页面
- AC-3: 待清理页展示倒计时+撤销+永久删除按钮
- AC-4: 永久删除(MEDIA_SYSTEM_DELETED) → DB记录+评论+关系+MinIO对象全部清除
- AC-5: 永久删除(相册类) → 相册结构+评论+关系+trash记录清除，不删全局媒体
- AC-6: purge 后 trash_items 表中无残留记录
- AC-7: purge 后 MinIO 中无残留对象（通过对象 key 核验）

**涉及文件**:
- `feature/photos/RealTrashListScreen.kt`（FR-1 拆分后）— 待清理入口
- `feature/photos/RealTrashPendingCleanupScreen.kt`（FR-1 拆分后）— 待清理页面
- `service/trash/TrashService.java` — purge 逻辑验证/修复（如需要）
- `service/upload/LocalMediaStorageService.java` — 物理文件删除验证

---

### FR-10: 恢复/移除后端关系处理

**描述**: 恢复和从回收站移除时，后端要及时处理好关联关系（评论目标/小相册关系/系统媒体导入状态/照片流去重等）。

**端**: Both

**优先级**: P0

**验收标准**:
- AC-1: 恢复媒体后 → 评论目标恢复、post_media 关系恢复、封面设置恢复
- AC-2: 恢复小相册后 → 大相册关系恢复、媒体关系数量正确
- AC-3: 恢复大相册后 → 子小相册全部恢复、systemKey 冲突处理正确
- AC-4: 移出回收站(remove)后 → 数据保持软删状态，等待 purge 或 undo
- AC-5: 恢复系统媒体后 → 照片流不重复（指纹去重）
- AC-6: 恢复系统媒体后 → 系统媒体导入状态标记更新
- AC-7: undo-remove 后 → 回到 IN_TRASH 状态，所有关系恢复

**涉及文件**:
- `service/trash/TrashService.java` — restore/moveOutOfTrash/undoRemove 逻辑验证
- `feature/photos/RealTrashViewModels.kt`（或 FR-2 重构后）— 前端状态同步
- `feature/photos/SystemMediaRepository.kt` — 导入状态刷新

## 三、非功能需求

### NFR-1: 编译性能
拆分后 Android 增量编译时间不应显著增加（目标：增量编译 < 90 秒）。

### NFR-2: 数据清理彻底性
purge 操作必须清理所有关联数据（DB 记录+评论+关系+物理文件+trash 记录），不留僵尸数据。

### NFR-3: 向后兼容
所有变更不得破坏现有入口（通知→回收站、照片流→回收站）。
