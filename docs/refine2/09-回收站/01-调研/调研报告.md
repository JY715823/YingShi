## 二、用户流程

### 流程1: 删除媒体/相册 → 进入回收站
用户删除媒体或小相册/大相册 → 后端 TrashService 创建 TrashItem(state=IN_TRASH) → 软删数据(设deletedAt) → 推送通知对方 → 回收站列表展示。

涉及: `TrashService.deleteLargeAlbum()/deleteSmallAlbum()/deleteSmallAlbumMedia()/systemDeleteMedia()`, `TrashItemEntity`, `TrashController`

### 流程2: 查看回收站列表
用户进入回收站 → 选择分类(四类Tab) → 后端 GET /api/trash/items?itemType=xxx → 展示列表 → 切换分类时先显示缓存内容+后台刷新。

涉及: `RealTrashListViewModel`, `RealTrashScreens.kt`, `TrashController.listTrash()`

### 流程3: 恢复回收站条目
用户点击"恢复" → 后端 POST restore → 按类型恢复数据(相册/媒体/关系) → state→RESTORED → 照片流/相册更新。

涉及: `TrashService.restoreTrashItem()`, 四种 restore 方法

### 流程4: 两阶段删除(移出→待清理→永久删除)
用户在回收站点击"移出回收站" → 后端 POST remove → state→PENDING_CLEANUP + 24h倒计时 → 分类菜单出现"待清理"入口 → 进入待清理页 → 可"撤销移出"(回到回收站)或"永久删除"(物理清理)。

涉及: `TrashService.moveOutOfTrash()`, `PendingCleanupScheduler`, `purgeTrashItem()`

### 流程5: 离线查看
用户在线时打开过回收站详情 → 缓存写入 → 断网后进入回收站 → 显示缓存内容(只读) → 写操作按钮禁用/提示只读。

涉及: `RealTrashListViewModel` 缓存逻辑, `AppReadCacheStore`

## 三、数据流向

### 前后端数据流
```
[删除操作] → TrashService 创建 TrashItem(IN_TRASH) + 软删数据
                    ↓
[回收站列表] ← GET /api/trash/items (按itemType筛选)
                    ↓
[恢复] → POST restore → 按类型恢复数据 → state→RESTORED
[移出] → POST remove → state→PENDING_CLEANUP + 24h倒计时
[撤销] → POST undo-remove → state→IN_TRASH
[永久删除] → POST purge → 物理清理(DB+MinIO) → 删除TrashItem
                    ↓
[自动清理] → PendingCleanupScheduler(每10min) → 过期条目自动purge
```

### 四类 item type 的 purge 差异

| 类型 | purge 操作 | 删物理文件 | 删全局媒体 |
|------|-----------|-----------|-----------|
| LARGE_ALBUM_DELETED | 硬删大相册+子小相册记录/关系/评论 | 否 | 否 |
| SMALL_ALBUM_DELETED | 硬删小相册记录/关系/评论 | 否 | 否 |
| MEDIA_REMOVED | 空操作(关系已删) | 否 | 否 |
| MEDIA_SYSTEM_DELETED | 硬删媒体记录+评论+物理文件 | **是** | **是** |
