## 一、FR-6: Viewer 退出导航 Bug 调研

### 1.1 根因分析（三层叠加）

**根因 A（结构性）**: TrashDetailScreen 用互斥 `when` 分支渲染，销毁了 PhotosRootScreen
- `YingShiApp.kt` L1364 的 `when { }` 是互斥条件分支
- `trashDetailRoute != null ->` (L1503) 与 `else ->` (L1527，含 PhotosRootScreen) 互斥
- 进入回收站详情时 PhotosRootScreen 被整体移出组合，HorizontalPager 状态（Tab 位置）销毁
- 返回时 PhotosRootScreen 从零重建，初始 Tab 完全由 `photosTopDestinationName` 决定
- 对比：照片流 Viewer (L1828) 是 `else` 分支内的覆盖层，PhotosRootScreen 保活

**根因 B（状态同步缺失）**: `onSelectedTopDestinationChange` 是空操作
- `PhotosRootScreen.kt` L144: `val onSelectedTopDestinationChange: (String) -> Unit = { /* handled by pager */ }` —— 空操作
- L280-285 的 `LaunchedEffect(pagerState.currentPage)` 检测到 Tab 切换但调用 no-op，**从不回写父级 `photosTopDestinationName`**
- 用户手动滑到回收站 Tab 后，`photosTopDestinationName` 仍是默认值 "PHOTOS"
- 叠加根因 A：返回时 `initialPage = PhotosTopDestination.valueOf("PHOTOS").ordinal = 0`，Pager 起始页落到照片 Tab
- 同时 `onOpenTrashDetail` (YingShiApp.kt L1588-1591) 也未在进入详情时把 `photosTopDestinationName` 校正为 TRASH

**根因 C（AC-4 特有）**: trashDetailRoute BackHandler 误调 `restoreNotificationCenter()`
- `YingShiApp.kt` L1037-1042: trashDetailRoute 的 BackHandler 在关闭详情后额外调用 `restoreNotificationCenter()` (L399-406)
- 用户从通知中心进入回收站详情时，`notificationTargetReturnRoute` 非空，该函数会把 `notificationCenterRoute` 恢复为通知中心快照
- `when` 块命中 L1405 的 `notificationCenterRoute != null` 分支，通知中心覆盖层重新出现，破坏 AC-4

## 二、FR-9: 待清理入口消失 + purge 彻底性调研

### 2.1 待清理入口消失根因

**主根因**: `RealTrashViewModels.kt:661` 的 `CachedTrashList.toUiState()` 中 `pendingEntries = emptyList()` 硬编码

- `refresh()` 在切换分类/初始加载/离线回退时走缓存分支
- `CachedTrashList` 结构不持久化 pending 数据
- 每次命中缓存，pendingEntries 必为空，入口消失

**次根因**: `RealTrashViewModels.kt:118-135` 主列表失败时 early-return 丢弃 pending 结果
- 即使 `getPendingCleanupItems` 并行请求成功，只要主列表失败就 return
- pending 结果永不上应用

**门控条件**: `RealTrashListScreen.kt:894` `if (pendingCount > 0)` 硬门控
- API 返回前 pendingCount=0，入口不渲染

**服务端查询逻辑无误**: `TrashService.java:328-333` + `TrashItemRepository.java:29-30` 按 `state=PENDING_CLEANUP` 正确查询

### 2.2 purge 操作清理范围（按类型）

| 资源 | MEDIA_SYSTEM_DELETED | SMALL_ALBUM_DELETED | LARGE_ALBUM_DELETED | MEDIA_REMOVED |
|------|---------------------|--------------------|--------------------|--------------|
| trash_items 记录 | ✅ | ✅ + 子 MEDIA_REMOVED | ✅ + 子 MEDIA_REMOVED | ✅（仅自身） |
| media 记录 | ✅ | ❌ **不删** | ❌ **不删** | N/A（保留） |
| post_media 关系 | ✅ | ✅ | ✅ | N/A |
| comments 评论 | ✅ | ✅ | ✅ | ❌ 不删（合理） |
| post 记录 | N/A | ✅ | ✅ | N/A |
| album 记录 | N/A | N/A | ✅ | N/A |
| MinIO 文件 | ✅ | ❌ **不删** | ❌ **不删** | N/A |

### 2.3 purge 遗漏清单

1. **SMALL_ALBUM_DELETED purge 不删子媒体物理文件与 media 记录** (`TrashService.java:511-517`)
   - 只删了 post_media + comments + post 本身，media 表记录和 MinIO 对象全部残留
   - 导致 DB 孤儿 media 记录 + MinIO 存储泄漏

2. **LARGE_ALBUM_DELETED purge 同样不删子媒体物理文件与 media 记录** (`TrashService.java:519-528`)
   - 对每个小相册调用的仍是 `purgeMediaRemovedItemsForSmallAlbum`（只删 trash_items）+ 删关系/评论/post
   - 未调用 `purgeMediaSystemDeleted` 级联删除媒体文件

3. **大/小相册 purge 不级联清理相册内 MEDIA_SYSTEM_DELETED trash_items**
   - 只清理子 MEDIA_REMOVED 类型（`purgeMediaRemovedItemsForSmallAlbum` 按 `itemType = MEDIA_REMOVED` 过滤）
   - 相册内系统删除媒体产生的 MEDIA_SYSTEM_DELETED trash_items 留下孤儿记录

4. **MEDIA_REMOVED purge 空实现** (`TrashService.java:530-533`)
   - by design（媒体仍可能被照片流/其他 post 引用）
   - 需在文档明确：purge MEDIA_REMOVED 仅删 trash 记录，不删媒体

### 2.4 MinIO 对象删除彻底性

**本地 provider（较彻底）** `LocalMediaStorageService.java:594-640`:
- 删原图 + 扫描 `previews` 目录按 cacheKey 前缀全删所有尺寸 preview/cover

**远程 MinIO provider（不彻底）** `LocalMediaStorageService.java:863-879`:
- 只删 3 个固定对象：原图 + 1280 预览 + 1280 封面
- **遗漏**: 其他尺寸变体（256/512/1024 等）+ cover-v1 旧版封面
- 需改为按 `previews/{yyyy}/{MM}/` 前缀列出 `{cacheKey}-*` 对象批量删除

### 2.5 现有测试覆盖

`TrashIntegrationTest.java`:
- `moveToPendingCleanupAndPurge` (L93) — move → purge
- `purgeDirectlyFromInTrash` (L144) — IN_TRASH 直接 purge
- `largeAlbumDeletedFullLifecycle` (L189) — 大相册完整生命周期
- **缺口**: 无测试验证 purge 后 media 记录/MinIO 文件/孤儿 trash_items 清理

## 三、FR-10: 恢复/移除后端关系处理调研

### 3.1 restore 各类型逻辑

| LARGE_ALBUM_DELETED | `restoreLargeAlbumDeleted` (L427-454) | 恢复大相册+子小相册，systemKey 冲突处理（清空） | ✅ 基本完整 |

| MEDIA_SYSTEM_DELETED | `restoreMediaSystemDeleted` (L471-509) | 恢复媒体本体 + post_media 关系 + 封面，指纹冲突去重 | ⚠️ 有缺陷 |

### 3.2 MEDIA_SYSTEM_DELETED 指纹冲突分支缺陷

`TrashService.java:476-486`: 检测到同指纹活跃媒体时，直接物理删除当前恢复的媒体，**未把原 snapshot 中的 `post_media` 关系迁移到已存在的媒体上**，原小相册封面也不会恢复到已存在媒体。

用户原以为"恢复"会让原小相册重新出现该媒体，实际原关系彻底丢失。

### 3.3 moveOutOfTrash 逻辑

`TrashService.java:271-283`:
- 仅允许 `IN_TRASH` 状态
- 改 state 为 `PENDING_CLEANUP`，设置 `removedAt`/`undoDeadlineAt`
- **不触碰任何业务数据**（album/post/media/post_media/comment 均不变）
- ✅ 符合预期（保持软删状态）

### 3.4 undoRemove 逻辑

`TrashService.java:311-325`:
- 仅允许 `PENDING_CLEANUP` 状态，校验 `undoDeadlineAt` 未过期
- 改回 `IN_TRASH`，清空 `removedAt`/`undoDeadlineAt`
- **不重新执行关系恢复**（因为 moveOutOfTrash 从未破坏关系）
- ✅ 符合预期

### 3.5 跨模块交互缺陷

**SyncModule 缺失 SYSTEM_MEDIA**:
- `SyncVersionTracker.kt:25-31`: 枚举只有 `PHOTO_FEED, ALBUMS, TRASH, NOTIFICATIONS, LIFE_CONSOLE`
- `RealTrashListScreen.kt:668-677` restore 只通知 `PHOTO_FEED, ALBUMS, TRASH, NOTIFICATIONS`
- `SystemMediaViewModel` 未监听 `SyncVersionTracker.staleState`
- `SystemMediaRepository.loadMedia` 默认走缓存
- **结果**: restore 后系统媒体页导入状态不自动刷新，需手动下拉

### 3.6 现有测试覆盖
