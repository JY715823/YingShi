## 二、FR-5 详细实施计划

### FR-5: AUTH_ACCOUNT_LOCKED 错误码前端处理

**目标**: Android 端识别 AUTH_ACCOUNT_LOCKED 错误码，显示中文提示并禁用登录按钮，直至用户重新尝试登录；两端契约文档补齐该错误码说明。

#### 变更1: LoginScreen.kt — 新增 isAccountLocked 状态

**位置**: L159 后（紧邻 `nowMillis` 声明）
**变更内容**:
```kotlin
var isAccountLocked by rememberSaveable { mutableStateOf(false) }
```

**设计理由**:
- 使用 `rememberSaveable`（非 `remember`）：配置变更（屏幕旋转）后保留锁定状态，按钮持续禁用
- 独立状态而非复用 errorMessage：errorMessage 有 16 处清除点（L172/232/243/270/324/360/393/423/445/471/526/535/557/585/703/750），复用会导致锁定状态被意外清除
- Boolean 类型：仅作按钮禁用标志位，不承载时间信息（服务端不返回剩余时间）

#### 变更2: LoginScreen.kt — handleActionError 增加锁定分支

**位置**: L208-221（handleActionError 函数）
**变更内容**:
```kotlin
fun handleActionError(result: ApiResult.Error) {
    val effectiveCode = result.code
    if (
        effectiveCode == "AUTH_LOGIN_CODE_EXPIRED" ||
        effectiveCode == "AUTH_LOGIN_CHALLENGE_INVALID"
    ) {
        clearChallenge()
    }
    if (effectiveCode == "AUTH_ACCOUNT_LOCKED") {
        isAccountLocked = true
        errorMessage = "账号已临时锁定，请 15 分钟后再试"
    } else {
        errorMessage = result.message
    }
    statusMessage = null
    pendingAction = null
    waitingForNetwork = false
    isLoading = false
}
```

**设计理由**:
- 锁定分支优先于通用回退：先检查 AUTH_ACCOUNT_LOCKED 设置中文文案，其余错误码走原逻辑透传 message
- isAccountLocked 仅在此处置为 true：不在其他地方设置 true，确保锁定状态唯一来源
- errorMessage 仍承载显示文案：currentMessage (L165) 优先取 errorMessage，UI 显示无需改动
- 文案"账号已临时锁定，请 15 分钟后再试"：符合 NFR-3 中文化，因服务端不返回剩余时间故用通用 15 分钟文案

#### 变更3: LoginScreen.kt — queueAction 重置锁定状态

**位置**: L441-448（queueAction 函数）
**变更内容**:
```kotlin
fun queueAction(action: PendingLoginAction) {
    actionNonce += 1
    pendingAction = action
    waitingForNetwork = false
    errorMessage = null
    statusMessage = null
    isAccountLocked = false
    launchPendingAction(actionNonce, action)
}
```

**设计理由**:
- 用户在锁定期间点击按钮（按钮不应可点击，但防御性处理）或锁定解除后重试时，queueAction 是所有登录动作的入口
- 重置 isAccountLocked=false：允许新一轮登录尝试，若仍锁定则服务端再次返回 AUTH_ACCOUNT_LOCKED，handleActionError 重新设置 true
- 实现 AC-4（锁定解除后可正常重试）：锁定解除后用户点击登录 → queueAction 重置 → 按钮启用 → 服务端放行 → 登录成功

#### 变更4: LoginScreen.kt — 登录按钮禁用逻辑

**位置**: L659-663（YingShiPrimaryMistButton 的 enabled 参数）
**变更内容**:
```kotlin
enabled = if (challengeState == null) {
    account.isNotBlank() && password.isNotBlank() && !isLoading && !isAccountLocked
} else {
    verificationCode.length >= 6 && !isLoading && !isAccountLocked
},
```

**设计理由**:
- 两个分支（密码阶段 + 验证码阶段）都增加 `&& !isAccountLocked`：锁定期间无论在哪个阶段都禁用
- 实现 AC-2（锁定状态下登录按钮保持禁用）
- 按钮禁用是软禁用：用户修改账号/密码不会自动解除锁定，必须等待服务端锁定解除后重新点击登录（queueAction 重置）

**补充说明段**（在 Error Codes 列表后）:
```markdown
## Account Lockout

- Triggered by `POST /api/auth/login/challenge` after `app.auth.account-lockout.max-attempts` (default 5) consecutive password failures
- HTTP status: `429 Too Many Requests`
- Lock duration: `app.auth.account-lockout.lock-duration` (default 15 minutes)
- Failed counter resets to 0 on successful password validation or after lock expiry
- Verification code failures do NOT trigger account lockout (only invalidate the challenge)
- Response body does not include `lockedUntil` / remaining time — clients should show a generic "try again later" message
- Lock check happens before password validation in `AuthService.requireAccountNotLocked`
```
