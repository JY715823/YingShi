## 一、变更文件影响链

### 变更1: LoginScreen.kt — 新增 isAccountLocked 状态

```

    → 直接影响:

```

**影响说明**: 新增状态对现有逻辑零侵入，仅在三个点读写，不影响其他状态变量。

### 变更2: LoginScreen.kt — handleActionError 增加锁定分支

```
LoginScreen.kt: handleActionError() L208-221
    → 直接影响:
        - AUTH_ACCOUNT_LOCKED 错误码不再透传英文 message
        - errorMessage 改为中文文案"账号已临时锁定，请 15 分钟后再试"
        - isAccountLocked 置为 true
    → 间接影响:
        - currentMessage (L165) 显示 errorMessage → UI 显示中文锁定提示
        - AnimatedVisibility 包裹的 message 区域 (需确认) 会显示锁定文案
    → 必须测试的影响路径:
        - IA-1: 密码错误 5 次后第 6 次请求 → AUTH_ACCOUNT_LOCKED → 中文提示 + 按钮禁用
        - IA-2: 锁定期间请求 remembered login → AUTH_ACCOUNT_LOCKED → 中文提示
        - IA-3: 锁定期间请求 verify challenge → 不会触发锁定（验证码错误不锁定）
```

**影响说明**: 
- 原逻辑 `errorMessage = result.message` 被包裹在 else 分支中，仅 AUTH_ACCOUNT_LOCKED 走新分支，其余错误码行为不变
- 其余状态赋值（statusMessage/pendingAction/waitingForNetwork/isLoading）保持原样

### 变更3: LoginScreen.kt — queueAction 重置锁定状态

```
LoginScreen.kt: queueAction() L441-448
    → 直接影响:
        - 每次发起登录动作时 isAccountLocked 重置为 false
        - 按钮在用户重试时恢复可用
    → 间接影响:
        - 若服务端仍锁定，handleActionError 会再次设置 true（自愈循环）
        - 若服务端已解锁，登录正常进行
    → 必须测试的影响路径:
        - IA-4: 锁定期间用户修改账号 → queueAction → 按钮恢复 → 新账号可登录
        - IA-5: 锁定解除后用户点击登录 → queueAction → 服务端放行 → 登录成功
```

**影响说明**: queueAction 是所有登录动作的唯一入口（5 处调用：L627/639/647/683/692），在此重置可覆盖所有重试场景。

### 变更4: LoginScreen.kt — 按钮禁用逻辑

```
LoginScreen.kt: YingShiPrimaryMistButton.enabled L659-663
    → 直接影响:

        - 按钮视觉态变为 disabled
    → 间接影响:
        - 用户无法在锁定期间发起登录请求（减少无效请求）

    → 必须测试的影响路径:

        - IA-7: 锁定状态下点击按钮无响应（不触发 queueAction）
```

**影响说明**: 仅在原 enabled 表达式末尾追加 `&& !isAccountLocked`，原逻辑（account/password/isLoading/verificationCode）保持不变。

## 三、后端影响链

```
本次后端代码零改动，后端影响链为空。

服务端锁定机制现有实现（不改动）:
  AuthController.loginChallenge()
    → AuthService.requestLoginChallenge()
      → requireAccountNotLocked(user)  // 锁定检查
      → validatePassword(user, password)
        → 失败: recordFailedLogin(user) → 可能锁定
        → 成功: sendLoginCode(user)
  AuthController.loginRemembered()
    → AuthService.loginWithRememberedDevice()
      → requireAccountNotLocked(user)  // 锁定检查
      → validatePassword(user, password)
  AuthController.loginVerify()
    → AuthService.verifyLoginChallenge()
      → 不调用 requireAccountNotLocked（验证码错误不锁定）
```

**结论**: 后端无需测试影响路径，服务端行为与改动前完全一致。

## 六、风险评估

| # | 风险 | 严重度 | 缓解措施 |
|---|------|--------|---------|
| 1 | isAccountLocked 在配置变更后丢失 | 低 | 使用 rememberSaveable 而非 remember |
| 2 | 锁定期间用户杀掉 App 重开，按钮可点击 | 低 | 可接受：再次登录会重新触发锁定，自愈 |
| 3 | 中文文案"15 分钟"与服务端实际锁定时间不一致 | 低 | 服务端默认 15min，文案硬编码 15min；若服务端配置变更需同步文案 |
| 4 | errorMessage 被其他流程清除导致锁定提示消失 | 中 | isAccountLocked 独立状态控制按钮禁用，即使 errorMessage 被清除按钮仍禁用；用户可点击按钮（若 isAccountLocked 重置）触发 queueAction 重新进入流程 |
