> 覆盖需求: FR-1 + FR-2
> 分析维度: 直接影响、间接影响、必须测试路径、历史数据兼容性

## 一、FR-2 影响分析

### 1.1 直接影响（改动文件本身）

| 文件 | 改动内容 | 影响范围 |
|------|---------|---------|
| TrashSnapshotHelper.java | LargeAlbumDeletedSnapshot record 新增 mediaIds 字段 | record 构造器签名变更，所有调用点受影响 |
| TrashService.java | deleteLargeAlbum 传完整 mediaIds + 截断 relatedMediaIds | 仅本方法内部 |
| TrashService.java | purgeLargeAlbumDeleted 新增 mediaIds 维度清理 + fallback | 仅本方法内部 |
| TrashService.java | 新增 truncateMediaIdsForColumn + resolveMediaIdsForPurge 私有方法 | 新增代码，无既有影响 |

### 1.2 间接影响（依赖改动文件的代码）

#### 影响 1：LargeAlbumDeletedSnapshot 构造器调用点

**搜索结果**: 全代码库仅 1 处调用
- `TrashService.java` L126: `new TrashSnapshotHelper.LargeAlbumDeletedSnapshot(albumId, smallAlbumIds)`
- **影响**: 需同步改为 3 参数构造器
- **风险**: 低（单点调用，编译期可发现）

#### 影响 2：readLargeAlbumDeletedSnapshot 调用点

**搜索结果**: 全代码库仅 1 处调用
- `TrashService.java` L520: `snapshotHelper.readLargeAlbumDeletedSnapshot(item)`
- **影响**: readLargeAlbumDeletedSnapshot 内部调用 `readSnapshot(item.getSnapshotJson(), LargeAlbumDeletedSnapshot.class)`，Jackson 反序列化自动处理新字段
- **风险**: 无（Jackson 反序列化 record 时，缺失字段自动为 null）

#### 影响 3：restoreLargeAlbumDeleted 方法

**文件**: TrashService.java L428 附近
**分析**:
- restoreLargeAlbumDeleted 读取 snapshot 后，主要使用 `snapshot.albumId()` 和 `snapshot.smallAlbumIds()`
- **不使用 mediaIds**
- **影响**: 无需改动
- **风险**: 无

#### 影响 4：toTrashItemDto 方法

**文件**: TrashService.java L716 附近
**分析**:
- toTrashItemDto 读取 `item.getRelatedMediaIds()` 返回给前端
- FR-2 改动后 relatedMediaIds 为截断后的前 20 个
- **影响**: 前端对 LARGE_ALBUM_DELETED 类型看到的 relatedMediaIds 不完整（仅前 20）
- **风险**: 低（前端对 LARGE_ALBUM_DELETED 不消费 relatedMediaIds 字段，仅展示 title/previewInfo）

#### 影响 5：TrashMapper.resolveCommentTargetMediaId

**分析**:
- 对 LARGE_ALBUM_DELETED 类型直接返回 null
- **影响**: 不受影响
- **风险**: 无

### 1.3 历史数据兼容性

| # | 场景 | 历史数据状态 | FR-2 改动后行为 | 风险 |
|---|------|------------|---------------|------|
| 1 | 历史 trash item 的 snapshot JSON | `{"albumId":"xxx","smallAlbumIds":["a","b"]}`（无 mediaIds） | Jackson 反序列化 mediaIds = null | 无 |
| 2 | 历史 trash item 的 relatedMediaIds 列 | 可能含全量 mediaIds（未截断） | purgeLargeAlbumDeleted 的 fallback 读取此列 | 无（fallback 尽力清理） |
| 3 | 历史 trash item purge 时 | snapshot.mediaIds = null | resolveMediaIdsForPurge fallback 到 relatedMediaIds 列 | 无（可能清理不完整，但历史数据 purge 场景极少） |
| 4 | 新 trash item 的 snapshot JSON | `{"albumId":"xxx","smallAlbumIds":["a","b"],"mediaIds":["m1","m2",...]}` | purge 优先读 snapshot.mediaIds | 无 |
| 5 | 新 trash item 的 relatedMediaIds 列 | 前 20 个 mediaIds（截断） | 仅作摘要，purge 不依赖 | 无 |

**结论**: 历史数据完全兼容，无破坏性变更。

### 1.4 purgeLargeAlbumDeleted 双重清理策略分析

**改动前**: 仅按 smallAlbumId 维度清理（postMedia + comment + post）
**改动后**: 按 smallAlbumId 维度 + mediaId 维度双重清理

**分析**:
- 按 smallAlbumId 维度清理已覆盖 99% 场景（postMediaRepository.deleteByLibraryIdAndPostId 删除该小相册的所有媒体关系）
- 新增 mediaId 维度清理是**额外保障**，覆盖以下边界：
  - 媒体被多个小相册引用时，确保所有 postMedia 关系被清理
  - 评论按 mediaId 维度的孤儿数据清理
- **风险**: 低（deleteByLibraryIdAndMediaId 是幂等操作，重复删除无副作用）

## 二、FR-1 影响分析

### 2.1 直接影响（新建/扩展测试文件）

| 文件 | 改动类型 | 影响 |
|------|---------|------|
| AlbumIntegrationTest.java | 新建 | 新增测试类，不影响既有代码 |
| TrashIntegrationTest.java | 扩展 | 新增 3 个 @Test 方法 + 辅助方法，既有 6 个测试不变 |

### 2.2 间接影响（测试基础设施）

#### 影响 1：AbstractPostgresIntegrationTest 基类

**分析**:
- AlbumIntegrationTest 继承此基类，使用 `loginAndGetAccessToken()`、`readField()`、`jpegBytes()`
- **不改动基类**
- **影响**: 无（仅使用 protected 方法）

#### 影响 2：TestSeedDataInitializer 种子数据

**分析**:
- 种子数据预置 library_shared + user_demo_a（OWNER）+ user_demo_b（MEMBER）
- AlbumIntegrationTest 使用 ACCOUNT_A 登录，操作 library_shared
- **影响**: 测试创建的大相册/小相册会写入 library_shared
- **风险**: 低（Testcontainers 容器 JVM 级复用，但每个测试类运行后数据不清空，需注意测试间数据可见性）
- **缓解**: 测试用 jsonPath 按特定 title 筛选，不依赖"空库"状态

#### 影响 3：Testcontainers 容器共享

**分析**:
- AlbumIntegrationTest 和 TrashIntegrationTest 共享同一个 PG 容器
- 两个测试类创建的数据互相可见
- **风险**: 低（测试用独立 title/mediaId 避免冲突）
- **缓解**: 所有测试用 `System.nanoTime()` 生成唯一 fingerprint

### 2.3 测试执行影响

#### 影响 1：mvnw.cmd test 全量执行

**分析**:
- 新增 AlbumIntegrationTest（5 用例）+ TrashIntegrationTest 扩展（3 用例）= +8 用例
- 现有测试用例数：~21（Trash 6 + Auth 8 + Upload 5 + Ledger 2）
- 改后总用例数：~29
- **影响**: 测试执行时间增加约 30-40 秒（Testcontainers 启动后，每用例约 3-5 秒）

#### 影响 2：LiveServerIntegrationTest

**分析**:
- 该测试类直连 localhost:8080 运行中的 server，无 @Disabled 注解
- `mvnw.cmd test` 全量执行时可能失败（server 未运行）
- **影响**: 若失败，会阻塞 FR-1 AC-5（mvnw.cmd test 全部通过）
- **缓解**: 实施时检查，若失败则添加 `@Disabled("Requires running server")` 注解

## 五、风险矩阵

| # | 风险 | 严重度 | 可能性 | 缓解措施 |
|---|------|--------|--------|---------|
| 1 | LargeAlbumDeletedSnapshot 构造器签名变更遗漏调用点 | 高 | 低 | 编译期可发现，全库仅 1 处调用 |
| 2 | purgeLargeAlbumDeleted mediaIds 维度清理误删数据 | 高 | 低 | deleteByLibraryIdAndMediaId 幂等，仅删 postMedia 关系不删 media 本体 |

| 4 | Testcontainers 数据共享导致测试间冲突 | 中 | 低 | 使用 nanoTime 唯一标识 + jsonPath 筛选 |
