## 二、FR-2 代码精确定位

### LargeAlbumDeletedSnapshot 定义

**文件**：`E:/Study/App/YingShi-Server/src/main/java/com/yingshi/server/service/trash/TrashSnapshotHelper.java`
**行号**：L147-148

- 类型：Java `record`（TrashSnapshotHelper 内部嵌套）
- 序列化：Jackson ObjectMapper 写入 `TrashItemEntity.snapshotJson`（`text` 列，无长度限制）
- 当前字段（仅 2 个）：
  - `String albumId` — 被删除的大相册 ID
  - `List<String> smallAlbumIds` — 子小相册 ID 列表
- **关键发现：snapshot 不含 mediaIds 字段**

### deleteLargeAlbum 数据流

**文件**：`TrashService.java` L89-131

1. 查子小相册：`postRepository.findByLibraryIdAndAlbumIdAndDeletedAtIsNullOrderByDisplayTimeMillisDescUpdatedAtDesc`（L93-96）
2. 提取 smallAlbumIds（L97）
3. 查媒体 ID：`postMediaRepository.findByLibraryIdAndPostIdIn` → `mediaIds`（L98-104，去重）
4. 软删大相册 + 子小相册（L107-112）
5. 调用 `createTrashItem`（L114-127），传入 `relatedMediaIds = mediaIds`，`snapshot = new LargeAlbumDeletedSnapshot(albumId, smallAlbumIds)`（L126）

### createTrashItem 截断风险点

**文件**：`TrashService.java` L591

```java
item.setRelatedMediaIds(String.join(",", relatedMediaIds));
```

- `TrashItemEntity.relatedMediaIds` 字段：`@Column(length = 2000)`（domain/TrashItemEntity.java L44-45）
- DB 列：`related_media_ids varchar(2000)`（V1__initial_schema.sql L130）
- 媒体 ID 单条约 20-36 字符 + 逗号，**约 66 条即触发截断**
- 截断后果：PostgreSQL 抛 `value too long` 异常，删除大相册操作整体失败

### purgeLargeAlbumDeleted 数据流

**文件**：`TrashService.java` L519-528

1. `snapshotHelper.readLargeAlbumDeletedSnapshot(item)` 读取 snapshot（L520）
2. 遍历 `snapshot.smallAlbumIds()`（L521），对每个小相册：
   - `purgeMediaRemovedItemsForSmallAlbum`（L522）
   - `postMediaRepository.deleteByLibraryIdAndPostId`（L523）
   - `commentRepository.deleteByLibraryIdAndPostId`（L524）
   - `postRepository.delete`（L525）
3. `albumRepository.delete`（L527）

**关键发现：purgeLargeAlbumDeleted 完全不读取 relatedMediaIds**，只依赖 snapshot 的 smallAlbumIds 和 albumId。物理删除按 postId 维度执行。

### FR-2 改动点定位

| # | 文件 | 行号 | 改动内容 |
|---|------|------|---------|
| 1 | TrashSnapshotHelper.java | L147 | LargeAlbumDeletedSnapshot record 新增 `List<String> mediaIds` 字段 |
| 2 | TrashService.java | L126 | deleteLargeAlbum 构造 snapshot 时传入 mediaIds |
| 3 | TrashService.java | L591 | createTrashItem 中 relatedMediaIds 截断为前 20 个（摘要） |
| 4 | TrashService.java | L519-528 | purgeLargeAlbumDeleted 从 snapshot 读取 mediaIds（含 fallback 到 relatedMediaIds） |

### 历史数据兼容性

- Jackson 反序列化缺失字段时赋 null
- record 的 `List<String> mediaIds` 历史数据为 null
- purgeLargeAlbumDeleted 需做 null 防御：`mediaIds != null ? mediaIds : splitIds(item.getRelatedMediaIds())`

### 影响面分析

- `restoreLargeAlbumDeleted`（L428）：只读 snapshot.albumId 和 smallAlbumIds，**无需改动**
- `TrashMapper.resolveCommentTargetMediaId`：对 LARGE_ALBUM_DELETED 类型直接返回 null，**不受影响**
- `toTrashItemDto`（L716）：读 relatedMediaIds 返回给前端，截断后前端看到的 mediaIds 不完整，但**不影响功能**（前端对 LARGE_ALBUM_DELETED 不消费此字段）

## 七、技术约束与注意事项

1. **FR-2 历史数据兼容**：LargeAlbumDeletedSnapshot 新增 mediaIds 字段后，历史 snapshot JSON 不含此字段，Jackson 反序列化为 null。purgeLargeAlbumDeleted 需做 null 防御 + fallback 到 relatedMediaIds。

2. **relatedMediaIds 截断策略**：AC-2 要求"relatedMediaIds 截断为前 20 个"。需在 createTrashItem 或 deleteLargeAlbum 中实现截断逻辑。建议在 deleteLargeAlbum 调用 createTrashItem 前对 mediaIds 列表截断，保持 createTrashItem 通用性。

3. **测试种子数据**：TestSeedDataInitializer 只预置用户和库，不预置大相册。AlbumIntegrationTest 需通过 API 自建大相册。TrashIntegrationTest 扩展的 largeAlbumDeleted 测试也需先创建大相册 + 小相册 + 媒体。

4. **LiveServerIntegrationTest 风险**：若 `mvnw.cmd test` 全量执行时 LiveServerIntegrationTest 失败（server 未运行），需确认是否有 @Disabled 注解。若无，实施时可能需要排除。

5. **FR-2 改动顺序**：先改 TrashSnapshotHelper（加字段）→ 再改 TrashService.deleteLargeAlbum（传 mediaIds + 截断 relatedMediaIds）→ 最后改 purgeLargeAlbumDeleted（读 snapshot mediaIds + fallback）。编译验证后再写测试。

6. **Testcontainers 共享容器**：所有继承 AbstractPostgresIntegrationTest 的测试类共享同一个 PG 容器（JVM 级），测试数据可能互相影响。AlbumIntegrationTest 和 TrashIntegrationTest 的测试数据需注意隔离（如使用不同的 albumId，避免冲突）。
