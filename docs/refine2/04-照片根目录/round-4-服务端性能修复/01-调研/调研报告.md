## 一、FR-12: 服务端 N+1 查询修复 — 现状分析

### 1.1 resolveFirstVisibleMediaId — N+1 查询

**文件**: `TrashService.java` L681-L692

**当前逻辑**:
1. 查询所有 `PostMediaEntity` relations（1 次 SQL）
2. for-loop 遍历每条 relation，逐条调用 `mediaRepository.findByIdAndLibraryIdAndDeletedAtIsNull()`（N 次 SQL）
3. 找到第一条存在且未被删除的 media 即返回

**性能问题**: 如果有 N 条 relations，总共产生 N+1 次 SQL 查询（含 1 次 relations 查询 + N 次 media 逐条查询）。

**可用基础能力**:
- `MediaRepository.findByLibraryIdAndIdInAndDeletedAtIsNull()` (L26) — 已存在，支持批量查询，返回 `List<MediaEntity>`
- 该方法的签名：`List<MediaEntity> findByLibraryIdAndIdInAndDeletedAtIsNull(String libraryId, Collection<String> ids)`

**修复方案**: 先收集所有 relation 的 mediaId，用 `findByLibraryIdAndIdInAndDeletedAtIsNull` 一次批量查询，构建 `Set<String>` 存在集合，再遍历 relations 查找第一个在 Set 中的 mediaId。

### 1.2 purgeMediaRemovedItemsForSmallAlbum — 全量加载后 Java 过滤

**文件**: `TrashService.java` L546-L555

**当前逻辑**:
1. 查询所有 `state=IN_TRASH, itemType=MEDIA_REMOVED` 的 TrashItem（1 次 SQL，全量）
2. Java 层 `stream().filter()` 按 `sourcePostId` 过滤
3. `deleteAll()` 删除匹配项

**性能问题**: 全量加载所有 MEDIA_REMOVED 项，在数据量大时内存和网络开销显著。

**缺失能力**: `TrashItemRepository` 没有按 `sourcePostId` 过滤的查询方法。

**修复方案**: 新增 `findByLibraryIdAndStateAndItemTypeAndSourcePostId()` 方法，将过滤下推到 SQL 层。

### 1.3 TrashItemRepository 现状

**文件**: `TrashItemRepository.java` L1-L45

已有相关方法：
- `findByLibraryIdAndStateAndItemType(libraryId, state, itemType)` — 返回 List，无 sourcePostId 过滤
- `findByLibraryIdAndStateAndItemType(libraryId, state, itemType, pageable)` — 返回 Page，带分页

**需新增方法**: `findByLibraryIdAndStateAndItemTypeAndSourcePostId(String libraryId, TrashItemState state, TrashItemType itemType, String sourcePostId)` — 返回 `List<TrashItemEntity>`

### 1.4 MediaRepository 现状

**文件**: `MediaRepository.java` L1-L114

已有批量查询方法：
- `findByLibraryIdAndIdIn(libraryId, ids)` (L24) — 不检查 deletedAt
- `findByLibraryIdAndIdInAndDeletedAtIsNull(libraryId, ids)` (L26) — 检查 deletedAt，**直接可用**

**无需新增方法**。

## 二、FR-13: 上传历史列表真分页 — 现状分析

### 2.1 UploadController.listUploads — 伪分页

**文件**: `UploadController.java` L54-L74

**当前逻辑**:
- 接收参数：`state`、`operationType`、`pageSize`
- 调用 `uploadService.listUploadHistory()` 获取全量数据
- 返回 `new PageInfo(1, items.size(), null, false)` — **硬编码伪分页**
  - `page` 固定为 1
  - `pageSize` 为实际返回条数
  - `nextCursor` 永远为 null
  - `hasMore` 永远为 false

**修复方案**:
- 新增 `cursor` 请求参数（可选）
- 将 `cursor` 透传给 Service 层
- 返回真实的 `PageInfo`（含 nextCursor 和 hasMore）

### 2.2 UploadService.listUploadHistory — 无分页支持

**文件**: `UploadService.java` L170-L194

**当前逻辑**:
- 参数：`currentUser`、`rawState`、`rawOperationType`、`requestedPageSize`
- 调用 `uploadTaskRepository.findVisibleHistory()` 获取全量数据
- `.stream().limit(pageSize)` 在 Java 层截断 — 仍是全量查询

**修复方案**:
- 新增 `cursor` 参数
- 使用 `PageRequest.of(0, pageSize)` 或自定义 cursor 查询实现真分页
- 查询 `pageSize + 1` 条记录来判断 hasMore

### 2.3 UploadTaskRepository.findVisibleHistory — 无 cursor

**文件**: `UploadTaskRepository.java` L46-L62

**当前查询**:
```sql
select task from UploadTaskEntity task
where task.libraryId = :libraryId
  and task.uploadedByUserId = :uploadedByUserId
  and task.dismissedAt is null
  and task.updatedAt >= :updatedAfter
  and (:state is null or task.state = :state)
  and (:operationType is null or task.operationType = :operationType)
order by task.updatedAt desc, task.id desc
```
- 无 cursor 参数
- 无 Pageable 参数
- 返回全量数据（仅受 `updatedAfter` 30 天限制）

**修复方案**:
- 新增 `findVisibleHistoryPage` 方法，接收 `Pageable` 参数
- 使用 `PageRequest` 实现分页，`pageSize + 1` 判断 hasMore
- cursor 使用 `updatedAt` + `id` 组合（与现有排序一致）

### 2.4 UploadTaskEntity — cursor 可用性

**文件**: `UploadTaskEntity.java` L1-L303

关键字段：
- `id`: String（可用于 cursor 末尾值）
- `updatedAt`: Instant（继承自 LibraryScopedEntity 的 createdAt/updatedAt）
- `dismissedAt`: Instant

**cursor 方案**: 使用 `updatedAt` + `id` 复合 cursor（与 `order by updatedAt desc, id desc` 排序一致）。cursor 编码为 `updatedAt_epochMillis:id` 字符串。

### 2.5 Android 端影响评估

**UploadApi.kt** (L37-L42):
```kotlin
@GET("api/uploads")
suspend fun getUploadHistory(
    @Query("state") state: String? = null,
    @Query("operationType") operationType: String? = null,
    @Query("pageSize") pageSize: Int? = null,
): ApiEnvelopeDto<List<UploadTaskDto>>
```

**关键发现**:
- 返回类型是 `ApiEnvelopeDto<List<UploadTaskDto>>`，**不是** `ApiEnvelopeDto<PageInfoDto<...>>`
- 没有 `cursor` 参数
- `Contracts.kt` 接口定义：`getUploadHistory` 返回 `ApiResult<List<RemoteUploadTask>>`（无 PageInfo）
- `RealRepositories.kt` 实现：直接取 `.data` 字段，不访问 PageInfo
- `LocalSystemMediaBridgeRepository.kt` 调用方：使用 `pageSize=100`，不依赖 hasMore/nextCursor

**结论**: Android 端**完全不依赖** PageInfo 的 hasMore/nextCursor 字段。后端新增 cursor 参数且向后兼容（不传 cursor 时返回首页），Android 端无需任何改动即可正常工作。
