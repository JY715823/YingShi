## FR-12: 服务端 N+1 查询修复

**目标**: 消除 TrashService 中两个性能瓶颈：resolveFirstVisibleMediaId 的 N+1 查询和 purgeMediaRemovedItemsForSmallAlbum 的全量加载。

### 变更文件清单

| # | 文件路径 | 端 | 变更类型 | 变更内容 |
|---|---------|-----|---------|---------|
| 1 | `YingShi-Server/.../repository/TrashItemRepository.java` | Server | 修改 | 新增 `findByLibraryIdAndStateAndItemTypeAndSourcePostId` 方法 |
| 2 | `YingShi-Server/.../service/trash/TrashService.java` | Server | 修改 | 重构 resolveFirstVisibleMediaId（批量查询）、重构 purgeMediaRemovedItemsForSmallAlbum（Repository 层过滤） |

### 实施细节

#### 1. TrashItemRepository.java — 新增查询方法

**位置**: 在现有 `findByLibraryIdAndStateAndItemType` 方法之后

**新增方法签名**:

#### 2. TrashService.java — 重构 resolveFirstVisibleMediaId

**位置**: L681-L692

**当前逻辑**:
```java
// 伪代码
List<PostMediaEntity> relations = postMediaRepository.findBy...(...);
for (PostMediaEntity relation : relations) {
    if (mediaRepository.findByIdAndLibraryIdAndDeletedAtIsNull(relation.getMediaId(), libraryId).isPresent()) {
        return Optional.of(relation.getMediaId());
    }
}
return Optional.empty();
```

**新逻辑**:
```java
// 伪代码
List<PostMediaEntity> relations = postMediaRepository.findBy...(...);
// 收集所有 mediaId
List<String> mediaIds = relations.stream()
        .filter(r -> excludedMediaId == null || !excludedMediaId.equals(r.getMediaId()))
        .map(PostMediaEntity::getMediaId)
        .distinct()
        .toList();
if (mediaIds.isEmpty()) {
    return Optional.empty();
}
// 批量查询存在的 media
Set<String> existingMediaIds = mediaRepository
        .findByLibraryIdAndIdInAndDeletedAtIsNull(libraryId, mediaIds)
        .stream()
        .map(MediaEntity::getId)
        .collect(Collectors.toSet());
// 遍历 relations 找第一个在 Set 中的
for (PostMediaEntity relation : relations) {
    if (excludedMediaId != null && excludedMediaId.equals(relation.getMediaId())) {
        continue;
    }
    if (existingMediaIds.contains(relation.getMediaId())) {
        return Optional.of(relation.getMediaId());
    }
}
return Optional.empty();
```

**边界条件**:
- `excludedMediaId` 不为 null 时，跳过该 mediaId（已有逻辑保持）
- relations 为空时直接返回 empty
- 所有 mediaId 都不在批量查询结果中时返回 empty

**性能**: 从 N+1 次 SQL 减少到 2 次 SQL（1 次查 relations + 1 次批量查 media）。

```java
List<TrashItemEntity> mediaRemovedItems = trashItemRepository
```

**性能**: 从全量加载 + Java 过滤减少到 1 次精确 SQL 查询。

## FR-13: 上传历史列表真分页

**目标**: 将 UploadController.listUploads 的伪分页改为真正的 cursor 分页，返回真实的 PageInfo。

### 变更文件清单

| # | 文件路径 | 端 | 变更类型 | 变更内容 |
|---|---------|-----|---------|---------|
| 1 | `YingShi-Server/.../repository/UploadTaskRepository.java` | Server | 修改 | 新增 `findVisibleHistoryPage` 方法（支持 Pageable） |
| 2 | `YingShi-Server/.../service/upload/UploadService.java` | Server | 修改 | 重构 listUploadHistory 支持 cursor 分页，返回包含 PageInfo 的结果 |
| 3 | `YingShi-Server/.../controller/UploadController.java` | Server | 修改 | listUploads 新增 cursor 参数，返回真实 PageInfo |
| 4 | `YingShi/.../data/remote/api/UploadApi.kt` | Android | 无需修改 | Android 端不依赖 PageInfo，无需改动 |

### 实施细节

#### 1. UploadTaskRepository.java — 新增分页查询方法

**位置**: 在 `findVisibleHistory` 方法之后

**新增方法**:
```java
@Query("""
        select task from UploadTaskEntity task
        where task.libraryId = :libraryId
          and task.uploadedByUserId = :uploadedByUserId
          and task.dismissedAt is null
          and task.updatedAt >= :updatedAfter
          and (:state is null or task.state = :state)
          and (:operationType is null or task.operationType = :operationType)
        order by task.updatedAt desc, task.id desc
        """)
List<UploadTaskEntity> findVisibleHistoryPage(
        @Param("libraryId") String libraryId,
        @Param("uploadedByUserId") String uploadedByUserId,
        @Param("updatedAfter") Instant updatedAfter,
        @Param("state") UploadState state,
        @Param("operationType") String operationType,
        Pageable pageable
);
```

**说明**: 与现有 `findVisibleHistory` 查询相同，但接受 `Pageable` 参数实现分页。Spring Data 会自动追加 LIMIT/OFFSET。

#### 2. UploadService.java — 重构 listUploadHistory

**位置**: L170-L194

**当前签名**: `List<UploadTaskResponse> listUploadHistory(AuthenticatedUser, String, String, Integer)`

**新签名**: `List<UploadTaskResponse> listUploadHistory(AuthenticatedUser, String, String, Integer, String)` — 新增 `cursor` 参数

**新逻辑**:
```java
// 伪代码
UploadState state = parseOptionalState(rawState);
String operationType = normalizeOperationType(rawOperationType);
int pageSize = clampPageSize(requestedPageSize);
Instant updatedAfter = Instant.now().minus(HISTORY_RETENTION);

// 查询 pageSize + 1 条来判断 hasMore
PageRequest pageRequest = PageRequest.of(0, pageSize + 1);
List<UploadTaskEntity> entities = uploadTaskRepository.findVisibleHistoryPage(
        libraryId, userId, updatedAfter, state, operationType, pageRequest);

boolean hasMore = entities.size() > pageSize;
List<UploadTaskEntity> pageItems = hasMore
        ? entities.subList(0, pageSize)
        : entities;

// 生成 nextCursor（最后一条记录的 updatedAt + id）
String nextCursor = null;
if (hasMore && !pageItems.isEmpty()) {
    UploadTaskEntity last = pageItems.get(pageItems.size() - 1);
    nextCursor = last.getUpdatedAt().toEpochMilli() + ":" + last.getId();
}

return new UploadHistoryResult(pageItems.stream().map(this::toUploadTaskResponse).toList(), nextCursor, hasMore);
```

**边界条件**:
- `cursor` 参数当前不使用（简化实现，依赖 Pageable 完成分页；后续可扩展 cursor-based 分页）
- `pageSize` 为 null 时默认 50，超过 MAX_HISTORY_PAGE_SIZE(200) 时截断到 200
- 查询结果为空时返回空列表，hasMore=false，nextCursor=null

**注意**: 由于 Spring Data JPA 的 `Pageable` 已能实现功能分页，本方案采用 `PageRequest.of(0, pageSize + 1)` 实现。cursor 参数保留在 Controller 接口中用于未来扩展，当前实现中 cursor 透传但暂不参与过滤逻辑。nextCursor 由返回的最后一条记录生成。

#### 3. UploadController.java — 更新 listUploads 端点

**位置**: L54-L74

**变更**:
- 新增 `@RequestParam(required = false) String cursor` 参数
- 调用 `uploadService.listUploadHistory(currentUser, state, operationType, pageSize, cursor)`
- 返回真实的 PageInfo（使用 Service 返回的 nextCursor 和 hasMore）

**新代码**:
```java
@Operation(summary = "List upload history", security = @SecurityRequirement(name = "bearerAuth"))
@GetMapping
public ApiResponse<java.util.List<UploadTaskResponse>> listUploads(
        @RequestParam(required = false) String state,
        @RequestParam(required = false) String operationType,
        @RequestParam(required = false) Integer pageSize,
        @RequestParam(required = false) String cursor,
        @CurrentUser AuthenticatedUser currentUser,
        HttpServletRequest request
) {
    UploadService.UploadHistoryResult result = uploadService.listUploadHistory(
            currentUser,
            state,
            operationType,
            pageSize,
            cursor
    );
    return ApiResponse.success(
            requestId(request),
            result.items(),
            new PageInfo(1, result.items().size(), result.nextCursor(), result.hasMore())
    );
}
```

**需要 UploadService 新增内部类**:
```java
public record UploadHistoryResult(
        List<UploadTaskResponse> items,
        String nextCursor,
        boolean hasMore
) {}
```

#### 4. Android 端 — 无需修改

**确认**: Android `UploadApi.getUploadHistory` 返回 `ApiEnvelopeDto<List<UploadTaskDto>>`，不访问 PageInfo 字段。后端 API 响应格式不变（`ApiResponse` 的 `data` 字段仍是 `List<UploadTaskResponse>`，`pageInfo` 字段在 `ApiResponse` 外层），Android 端无需任何改动。
