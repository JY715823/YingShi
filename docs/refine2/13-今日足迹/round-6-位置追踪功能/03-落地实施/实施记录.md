## 五、关键技术决策记录

### 5.1 Amap API Key 类型

- Android 端用 `FusedLocationProvider` (系统硬件能力, 不需要高德 Key) 拿 GPS 坐标
- 服务端用高德 **Web 服务 Key** `a658afca501f9337e964af99b3f2670f` 调 regeo API 反向地理编码
- 这是行业标准做法 (美团/字节/小红书等均采用), Android Key `d4f794bb299372394f06fe512949adba` 不适用此场景

### 5.2 反向地理编码 fallback 链

1. Android 上传时如果能拿到 GPS 坐标, 就把 lat/lng 传给服务端 (不传 label)
2. 服务端 UploadService.createUploadToken 把 lat/lng 存到 UploadTaskEntity
3. 服务端 UploadService.buildMediaFromTask (confirm 时触发):
   - 优先用 task.locationLabel (客户端预填)
   - 否则调 `geocodingService.reverseGeocode(lat, lng)`
   - 失败静默 (locationLabel = null), 不阻断上传
4. addBowelEvent 同样的 fallback 逻辑

### 5.3 withDisplayTime 高风险点

`LifeConsoleService.withDisplayTime(MediaDto source, long displayTimeMillis)` 在历史 API 中用于覆盖媒体展示时间。MediaDto 是 record, 必须手动重建。漏写任何字段都会丢失数据。

本轮在 record 末尾追加 3 个 location 字段后, 立即同步更新了 withDisplayTime — 这是历史 API 不丢位置的关键。

### 5.4 日级位置代表策略

历史页一天可能有多条媒体/事件, UI 上只展示一个位置胶囊。策略:
- 媒体历史: 当日所有媒体里, 取 `effectiveTimeMillis` 最大的且 `locationLabel` 非空的那条; self 优先于 partner (tie-breaking)
- 大便历史: 当日所有事件里, 取 `occurredAtMillis` 最大的且 `locationLabel` 非空的那条

### 5.5 Widget 不获取位置

`LifeConsoleWidgetProvider.kt` 在桌面 Widget 上点 "+1" 加排便事件时, **不调 LocationHelper**, 保持无参调用。原因: Widget 场景无 Activity 上下文, 不应触发权限弹窗; 且 Widget 多用于快速记账, 位置精度不重要。

### 5.6 测试环境 NoopGeocodingService 生效

测试环境 `AMAP_GEOCODING_ENABLED` 未设置 (默认 false), AmapGeocodingService 不注册, NoopGeocodingService fallback 生效, `reverseGeocode` 永远返回 null。这保证:
- 单元测试不依赖外部网络
- addBowelEvent 测试中 event.locationLabel = null, 不影响老断言
