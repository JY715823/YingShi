映世是一个双人私密相册与生活记录 App，服务一对亲密关系中的两个人。技术栈如下：

**Spring Boot 后端**（`E:\Study\App\YingShi-Server`）：

**部署**：

## 二、架构决策与技术约束

### 2.1 客户端 ↔ 服务端职责边界

| 功能域 | Android 客户端负责 | Spring Boot 服务端负责 |
|--------|------------------|---------------------|
| **认证** | 登录 UI、验证码输入、JWT 存储与自动刷新、设备记忆 | 登录挑战流、验证码发送（QQ 邮箱 SMTP）、JWT 签发/轮换、账号锁定、限流 |
| **照片流** | 分页加载、密度切换、时间滑条、多选操作、离线缓存 | keyset 分页查询、去重 feed、媒体存储（MinIO/S3）、视频封面生成（ffmpeg） |
| **上传** | multipart 上传（OkHttp 10min 超时、进度回调、可取消）、传输中心 UI、2 并发 Semaphore | 三段式 token→file→confirm/cancel、操作分组、过期清理 |
| **同步** | SyncVersionTracker 前台轮询 + FCM 触发即时 poll、按模块 staleness 追踪、StaleBanner | 单查询 GREATEST() 版本聚合 |
| **推送** | FCM 接收、通道管理、actor 自过滤、2min 去重、Fallback Notifier | FCM 发送、审计、偏好、诊断、self-fallback、after-commit async |
| **聊天导入** | QCE ZIP 解析、Silk 解码、Room 存储、媒体上传/下载 | ZIP 接收与解压、5 表存储（V25）、行级同步、媒体 HEAD/下载 |
| **账本** | Room v4 本地存储、RemoteLedgerSyncBridge（changelog + SharedFlow + 重试） | 9 表关系模型（V21）、增量同步、typed DTO |
| **回收站** | 24h 撤销 UI、离线缓存查看、恢复/移出/物理删除操作 | 三阶段（inTrash/pendingCleanup/restored）、4 种 itemType、调度清理 |

### 2.2 全栈协同约束

- **Retrofit 接口**：13 个接口定义，`AuthInterceptor` + `AuthRefreshCoordinator`（OkHttp authenticator 自动刷新 token）
- **Repository 双模式**：11 个接口 + Real + Fake + Provider，`RepositoryProvider.currentMode` 硬编码 `REAL`
- **Room 数据库**：`yingshi-ledger.db` v4（10 实体，3 个 Migration）、`yingshi-chat-imports.db` v3（5 实体，2 个 Migration）
- **错误处理**：`ApiResult.Error` 统一带 code/message/throwable，离线只读语义贯穿（`OfflineAccessManager`）
- **Docker 部署**：4 服务 docker-compose，容器内 `app.jar` 必须与 Flyway 版本一致（有过"容器落后源码"的教训）

### 2.3 编码规范

**Android (Kotlin/Compose)**：
- ViewModel 使用 `MutableStateFlow` + `asStateFlow()` + `viewModelScope.launch`
- Composables 渲染 state、emit events
- feature 包级划分（`feature/home`、`feature/photos`、`feature/life` 等）
- 设计 token 体系：Color/Shape/Theme/Tokens/Type 完整

**服务端 (Java/Spring Boot)**：
- Controller → Service → Repository → Domain 四层
- 自定义异常体系：~40 个 `ErrorCode` 枚举 + `GlobalExceptionHandler`
- DTO 按模块分子包，含 `@Size` 校验
- 迁移脚本在 `db/migration/postgresql/`，dev 用 H2 + ddl-auto:update

### 2.4 错误处理与降级策略

| 场景 | 失败类型 | 降级策略 | 重试策略 |
|------|---------|---------|---------|
| **JWT 刷新** | refresh token 过期 | 跳转重新登录页面 | 不自动重试 |
| **照片加载** | 网络超时 | Coil placeholder + 离线缓存 | 用户手动下拉刷新 |
| **上传** | 网络中断 | SharedPreferences 持久化任务状态，传输中心显示失败 | 用户手动重试 |
| **FCM 推送** | token 失效 | `disableInvalidTokens` 批量 saveAll 标记 | 下次推送自动跳过 |
| **同步** | 服务端不可达 | `OfflineAccessManager.state` 屏蔽写操作，`shouldFallbackToReadCache()` | FCM 触发 + 前台轮询 |
| **聊天导入** | 10GB ZIP 过大 | 前台 Service 保活 + 进度持久化 | 断点续传（待验证） |
| **回收站** | 对象存储删除失败 | 标记 pendingCleanup，调度重试 | 定时任务扫描 |

### 2.5 构建与部署约束

- **Release 强制 HTTPS**：`YINGSHI_RELEASE_API_BASE_URL` 环境变量必须配置 HTTPS URL，否则 `GradleException` 构建失败
- **google-services.json 条件化**：存在时才 apply google-services 插件
- **Docker 两阶段构建**：编译阶段装 ffmpeg + mvnw dependency:go-offline，运行阶段仅 JRE
- **docker-compose**：4 服务全部 `restart: unless-stopped`，端口绑 `127.0.0.1`，healthcheck 齐全
- **Profile 体系**：dev（H2）/ docker（PG + Flyway）/ docker-local（混合）/ prod

### 4.3 P1-3: 服务端并发与性能修复

**问题**：多个服务端并发/性能隐患。

#### 4.3.1 限流多实例兼容（P1-7）

- `ConcurrentHashMap` 单机内存限流在多实例部署下失效
- 方案 A（推荐）：迁移到 Redis 限流（引入 spring-data-redis + Bucket4j-redis 或自实现滑动窗口）
- 方案 B（最小改动）：文档化标注"当前限流仅单实例有效"，在部署文档中说明

#### 4.3.2 X-Forwarded-For 防伪（P1-8）

- 当前取首段 IP 可被伪造
- 在反向代理层覆盖 `X-Forwarded-For`（Nginx `proxy_set_header X-Forwarded-For $remote_addr`）
- 服务端添加 `trusted-proxies` 配置项，仅信任来自代理 IP 的 `X-Forwarded-For`

#### 4.3.3 notifiedUploadOperationKeys 内存泄漏（P1-9）

- `notifiedUploadOperationKeys` 无界 Set 缓慢增长
- 添加 TTL 过期机制：key 在 Set 中超过 24h 自动清除
- 或使用 Caffeine cache 替代 ConcurrentHashMap

#### 4.3.4 PushDispatchSupport ForkJoinPool sleep（P1-10）

- `afterCommitAsync` 使用 ForkJoinPool.commonPool() + Thread.sleep
- 改用 `@Async` + 自定义 ThreadPoolTaskExecutor（已在 `SchedulerConfig` 中配置 4 线程池）
- 或使用虚拟线程（Java 21 支持）

**验收标准**：
- [ ] 限流方案在部署文档中有明确说明（单实例或多实例方案）
- [ ] Nginx 配置模板中包含 `proxy_set_header X-Forwarded-For $remote_addr`
- [ ] notifiedUploadOperationKeys 有 TTL 或 maxSize 限制
- [ ] PushDispatchSupport 不再使用 ForkJoinPool.commonPool() 做 sleep

## 五、P2 需求规格（可接受延后）

> 以下需求已在 backend-platform.md 显式 defer，当前两人规模下可接受。列为 P2 的目的是在后续版本中有计划地处理。

### 5.1 P2-1: API 版本化

- 当前所有 API 在 `/api/` 下，无版本号
- 未来有破坏性变更时迁移到 `/api/v1/`
- **defer 理由**：无破坏性变更计划，需要时再加

### 5.2 P2-2: 分页标准化

- media feed 用 cursor 分页，其余用 offset 分页
- 客户端需处理两种模型
- **defer 理由**：cursor 分页在 media feed 上性能优势明显，其余列表数据量小，offset 足够

### 5.3 P2-3: ID 列宽度优化

- ID 列 `varchar(255)` 浪费存储，UUID 实际 ~38 字符
- **defer 理由**：迁移成本高（涉及所有 FK），两人规模下存储浪费可忽略

### 5.4 P2-4: Fake 体系清理

- `FakeAlbumRepository` ~1400 行等 Fake 实现保留但默认不调用
- 若确认不再切回 FAKE 模式，可全部删除
- **defer 理由**：不影响功能，清理是纯代码卫生工作

### 5.5 P2-5: 全局 object 单例重构

- `LocalSystemMediaBridgeRepository`、`OfflineAccessManager`、`AppReadCacheStore`、`GlobalPhotoFeedPageStateStore` 用 `object` + Compose `mutableStateOf` 做全局单例可观察状态
- 绕过 ViewModel，不利于测试与生命周期管理
- **defer 理由**：功能正确，重构风险大于收益

### 5.6 P2-6: dev seed 数据迁移

- dev seed 数据在 `src/main/java`（已 @Profile dev）
- 生产代码包含测试数据生成器
- **defer 理由**：@Profile 隔离，生产环境不加载，低风险

### 5.7 P2-7: dev profile schema drift

- dev profile `ddl-auto:update` 可能导致 H2 schema 与 PG Flyway 不一致
- **defer 理由**：仅影响 dev 环境，生产用 Flyway 管理

### 5.8 P2-8: 纯 UI 模块真机视觉

- life_home / profile-page / setting / today_trace 四个纯 UI 模块仅编译自检
- 真机视觉/动画/density 适配全部 carry-forward
- **defer 理由**：不影响功能，归入 P1-6 真机回归一并处理
