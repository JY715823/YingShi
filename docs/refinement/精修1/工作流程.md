## 一、总览

本工作流程将需求文档中的 **17 个实施模块 + 8 个 P2 defer 项** 划分为 **4 轮** 迭代实施。每轮遵循统一的 6 阶段流程：

```
调研 → 实施文档 → 落地实施 → 测试文档 → 落地测试 → 复检
```

### 四轮划分

| 轮次 | 名称 | 包含模块 | 预估工作日 | 定位 |
|------|------|---------|-----------|------|
| **Round 1** | P0 发布配置与安全加固 | R1-M1~M5 | 5-7 天 | Android 签名/混淆 + 服务端 CORS/HTTPS + V24 孤儿审计 + AGENTS.md 更新 |
| **Round 2** | P0 测试骨架与模块收口 | R2-M1~M4 | 8-12 天 | 服务端 Testcontainers 集成测试 + bin/noticeCenter/chatShower 三模块关闭 |
| **Round 3** | P1 代码质量与架构优化 | R3-M1~M4 | 5-8 天 | YingShiApp 拆分 + 服务端并发修复 + deprecated API 更新 |
| **Round 4** | P1 运营基础设施与上线准备 | R4-M1~M5 | 5-7 天 | CI/CD + 崩溃上报 + 真机回归 + 隐私说明 + 上线前终审 |

**四轮理由**：
- Round 1 全部是工程配置/脚本/文档类工作，**不涉及业务代码修改**，可快速完成且为后续轮次扫清障碍（签名配置是 assembleRelease 前提，CORS/HTTPS 是部署前提，V24 审计是生产迁移前提）
- Round 2 是工作量最大的一轮——服务端测试需要写代码 + Docker 环境，三个未关闭模块需要真机验证。但测试和模块关闭互相独立，可穿插进行
- Round 3 的代码质量修复（YingShiApp 拆分、并发修复）有一定重构风险，放在 Round 2 测试骨架之后可利用测试做回归保护
- Round 4 是上线前最后的收口工作，CI/CD 和崩溃上报是运维基础设施，真机回归是最终验收

## 三、每轮通用 6 阶段工作流

AI Agent 在每一轮中必须严格按照以下 6 个阶段顺序执行，**一个阶段完成后才能进入下一阶段**。每个阶段结束时，将产物写入对应文件夹。

### 阶段 1：调研

**目标**：深入理解本轮涉及的现有代码、构建配置、部署环境。

**输入**：
- [需求文档.md](./需求文档.md) 中本轮相关章节
- Android 代码：`E:\Study\App\YingShi\`
- 服务端代码：`E:\Study\App\YingShi-Server\`
- 存储/部署：`E:\Study\App\YingShi_Storage\`
- 精修记录：`E:\Study\App\YingShi\docs\refinement\*.md`

**调研清单（每轮必做）**：

1. **现有代码审查**：
   - 读取本轮涉及的所有源文件（Kotlin/Java/XML/YAML/Gradle）
   - 标注现有类/函数签名、数据流、异常处理方式
   - 确认 Flyway 迁移历史（V1–V25），找出需要新增的迁移编号
   - 检查是否有已废弃但未清理的代码

2. **构建/部署验证**：
   - 确认当前 `gradlew.bat assembleDebug` 编译通过
   - 确认当前 `mvnw.cmd compile` 编译通过
   - 确认 `docker compose up -d` 全栈可启动
   - 记录当前环境版本（JDK、Gradle、Docker、PG、MinIO）

3. **跨模块影响分析**：
   - 检查本轮改动是否影响其他 feature 模块
   - 确认 `RepositoryProvider`、`RemoteServiceFactory`、`AuthInterceptor` 等基础设施是否受影响
   - 检查 Flyway 迁移链是否连续

4. **依赖分析**：
   - 列出本轮模块依赖的所有 Gradle/Maven 包
   - 检查是否需要新增依赖
   - 确认新增依赖的版本兼容性

**产出**：
- `01-调研报告/调研报告.md`，包含：
  - 现有代码分析（每个文件/类/函数的状态、问题、改造点）
  - 构建/部署环境确认
  - 跨模块影响评估
  - 风险和注意事项

---

### 阶段 2：实施文档

**目标**：编写逐模块的详细实施方案，粒度到函数/配置级别。

**原则**：
- 每个模块独立一个 `.md` 文件
- 每个新增/修改的函数或配置项都要写清楚：签名/参数/值/异常/伪代码
- Flyway 迁移（如有）要写完整的 SQL + 回滚方案
- 标注该模块的验收标准（从需求文档中提取量化指标）

**实施文档模板**：

```markdown
# [模块名] 实施文档

## 一、目标
<!-- 2-3句话：这个模块要解决什么问题 -->

## 二、涉及文件清单
| 文件 | 端 | 改动类型 | 说明 |
|------|-----|---------|------|
| `app/build.gradle.kts` | Android | 修改 | 添加 signingConfigs... |
| `XxxController.java` | Server | 新增函数 | ... |

## 三、数据模型变更（如有）
<!-- 完整的 Flyway 迁移 SQL + 回滚 SQL -->

## 四、函数/配置级实施方案

### 4.1 新增/修改: `function_name()` 或 `配置项`
- **文件**: 完整路径
- **签名/格式**: 函数签名 或 配置 key-value
- **逻辑**: [伪代码/配置说明]
- **异常处理**: [列出可能的异常和处理方式]
- **调用/生效时机**: [谁调用/什么时候生效]

## 五、验收标准
- [ ] 从需求文档提取的量化指标1
- [ ] 从需求文档提取的量化指标2
```

**产出**：
- `02-实施文档/[模块名].md` × N

### 阶段 3：落地实施

**目标**：按照实施文档逐一修改项目代码和配置。

**原则**：
- **严格按实施文档执行**，不临时发挥
- Android 端每改完一组文件，立即 `gradlew.bat assembleDebug` 验证编译
- 服务端每改完一组文件，立即 `mvnw.cmd compile` 验证编译
- 遇到实施文档未覆盖的情况 → **暂停，先更新实施文档，再继续写代码**
- Flyway 迁移写完后验证正向可执行

**实施顺序**：
1. 数据模型 / Flyway 迁移（如有）
2. 服务端 Service/Controller 层修改
3. Android feature/data 层修改
4. 构建配置 / Gradle / Maven 修改
5. 部署配置 / Docker / Nginx 修改
6. 文档更新

**产出**：
- `03-实施记录/实施总结.md`，包含：
  - 实际修改的文件清单（含行号范围）
  - 与实施文档的偏差说明
  - 遇到的问题和解决方案
  - 未完成的遗留项

### 阶段 5：落地测试

**目标**：按照测试文档执行测试，记录结果。

**原则**：
- 服务端测试在 Docker 环境中运行（`docker compose up -d` 后 `mvnw test`）
- 单元测试必须全部通过
- 真机验证需要实际设备操作（或模拟器 + adb）
- 集成测试失败需分析根因，回阶段 3 修复
- 测试报告包含覆盖率数据（JaCoCo）

**产出**：
- `05-测试记录/测试报告.md`，包含：
  - 通过的测试数量 / 总数
  - 失败用例详情（输入、预期、实际、根因）
  - 代码覆盖率（JaCoCo 行覆盖率）
  - 真机验证截图和结果

---

### 阶段 6：复检

**目标**：对实施结果做全面审查，确保代码质量和需求覆盖。

**复检清单**：

1. **需求覆盖检查**：逐条核对需求文档的验收标准，确认全部达标
2. **代码质量检查**：
   - 是否有硬编码的魔法数字/字符串
   - 是否有未处理的异常路径
   - 是否有 SQL 注入风险（原生 SQL 需参数化）
   - 是否有未关闭的资源（连接/流/文件句柄）
   - Kotlin 代码是否有 `!!` 非空断言（应使用 `?.` 或 `let`）
3. **回归风险检查**：
   - 现有 API 接口是否仍然可用（curl 测试关键端点）
   - Flyway 迁移是否可重复执行（幂等性）
   - `docker compose up -d` 是否仍能正常启动
   - Android `assembleDebug` 是否仍能编译通过
4. **文档一致性检查**：
   - 实施文档与实际代码是否一致
   - 需求文档是否需要更新（如发现新的边界情况）
   - AGENTS.md 是否需要同步更新

**产出**：
- `06-复检报告/复检报告.md`，包含：
  - 需求覆盖率（已实现/总计）
  - 代码质量问题清单
  - 回归测试结果
  - 遗留问题（标注优先级和建议处理轮次）

**包含模块**：

| 代号 | 模块名 | 需求文档章节 | 预估工时 | 端 |
|------|--------|------------|---------|-----|

**执行顺序**：五个模块**互不依赖**，可并行实施。建议顺序：R1-M1 → R1-M2（Android 端一起处理）→ R1-M3 → R1-M4（服务端安全一起处理）→ R1-M5。

**阶段 1 调研重点**：

| 调研项 | 具体内容 |
|--------|---------|
| 当前 build.gradle.kts | 确认 signingConfigs、buildTypes、buildConfigFields 的现有配置 |
| 当前 proguard-rules.pro | 确认现有的 keep 规则 |
| BackendAutoLoginManager.kt | 确认 L30-32 的默认账号密码常量和所有引用方 |
| application.yml CORS 配置 | 确认 `app.cors.allowed-origins` 的现有值和 WebMvcConfig 中的 CORS 逻辑 |
| ProductionSafetyStartupCheck.java | 确认现有的安全检查项和 profile 判断逻辑 |
| Nginx/反向代理现状 | 确认当前是否有 Nginx 配置、HTTPS 证书情况 |
| V24__foreign_keys.sql | 确认 40+ 外键关系涉及的表对 |
| scripts/ 目录 | 确认现有运维脚本的风格和命名规范 |
| AGENTS.md | 确认当前内容和需要更新的部分 |

**阶段 3 实施顺序**：

```
第1步: R1-M1 创建签名密钥 + keystore.properties + build.gradle.kts signingConfigs
第2步: R1-M1 编写 ProGuard 规则 + 启用 minify/shrinkResources
第3步: R1-M1 修改 AndroidManifest.xml allowBackup=false
第4步: R1-M2 build.gradle.kts buildConfigField + BackendAutoLoginManager.kt 迁移
第5步: R1-M3 application.yml CORS 默认值 + ProductionSafetyStartupCheck 增加 CORS 检查
第6步: R1-M4 创建 Nginx HTTPS 配置模板 + docker-compose.prod.yml
第7步: R1-M5 编写 audit-orphans.sql + fix-orphans.sql
第8步: R1-M5 评估 V24 是否需要 NOT VALID
```

**关键风险**：
- ProGuard 规则不完整可能导致 release APK 运行时崩溃（Retrofit 接口被混淆、Room Entity 被移除等）
- 签名密钥丢失后无法更新已发布 APK，需妥善保管
- V24 孤儿审计可能发现大量孤儿数据，需要人工决策修复策略

### 5.1 每轮启动检查清单

在开始新轮次之前，AI Agent 必须确认：

- [ ] 本轮文件夹结构已创建（6 个子目录）

### 5.2 阶段间门禁

每个阶段完成后，**必须满足以下条件才能进入下一阶段**：

| 从 → 到 | 门禁条件 |
|---------|---------|
| 调研 → 实施文档 | 调研报告完整覆盖所有调研清单项 |
| 实施文档 → 落地实施 | 实施文档经审核（每个函数/配置有签名/值+逻辑+异常处理） |
| 落地实施 → 测试文档 | 所有计划修改的文件已实际修改，Android + Server 编译通过，Docker 容器能正常启动 |
| 测试文档 → 落地测试 | 每个模块的测试用例覆盖了正常路径、边界条件、异常路径 |
| 落地测试 → 复检 | 所有测试通过（失败用例有合理解释且已标注为非阻塞） |

### 5.3 编码规范

**Android (Kotlin/Compose)**：
- 遵循项目现有的 feature 包级结构
- ViewModel 使用 `MutableStateFlow` + `asStateFlow()` + `viewModelScope.launch`
- 避免 `!!` 非空断言，使用 `?.` 或 `let`
- 新增 Composable 添加 `@Preview` 函数
- 字符串不硬编码，使用 `strings.xml`

**服务端 (Java/Spring Boot)**：
- 遵循 Controller → Service → Repository → Domain 四层
- 新增异常使用自定义 `ErrorCode` 枚举 + `GlobalExceptionHandler`
- DTO 使用 `@Size` / `@NotNull` 等 Jakarta Validation 注解
- Flyway 迁移使用 PostgreSQL 方言，确保幂等性

**脚本/配置**：
- SQL 脚本放在 `scripts/` 目录，命名规范 `verb-object.sql`（如 `audit-orphans.sql`）
- PowerShell 脚本使用 `Verb-Noun.ps1` 命名
- Docker/Nginx 配置放在 `docs/deployment/` 或项目根目录

### 5.4 提交规范

- 同一模块的所有代码改动合并为一个 commit
- Commit message 格式：`[Round-X] R1-M1: Android 发布配置`
- 实施文档和代码在同一个 PR 中提交
- 签名密钥文件（`.jks`、`keystore.properties`）**绝不**提交
